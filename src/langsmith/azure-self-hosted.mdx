当您在使用 [Microsoft Azure](https://azure.microsoft.com/) 运行 LangSmith 时，您可以选择设置 [完全自托管](/langsmith/self-hosted) 或 [混合](/langsmith/hybrid) 模式。完全自托管模式会部署一个完整的 LangSmith 平台，包含可观测性功能以及创建 Agent 的部署选项。混合模式仅包含在您的云内部运行数据平面（Data Plane）中运行 Agent 所需的基础设施，而 SaaS 部分提供控制平面（Control Plane）和可观测性功能。

本页面提供了在 Azure 上部署和运行 LangSmith 的特定架构模式、服务建议和最佳实践。

<Note>
LangChain 提供了专门用于 Azure 的 Terraform 模块，以帮助您为 LangSmith 配置基础设施。这些模块可以快速设置 AKS 集群、Azure Database for PostgreSQL、Azure Managed Redis、Blob 存储以及网络资源。

请查看 [Azure Terraform 模块](https://github.com/langchain-ai/terraform/tree/main/modules/azure) 以获取文档和示例。
</Note>

## 参考架构

我们建议使用 Azure 的托管服务来提供一个可扩展、安全和有弹性的平台。以下架构适用于自托管和混合部署：

![Architecture diagram showing Azure relations to LangSmith services](/langsmith/images/azure-architecture-self-hosted.png)

- **客户端接口**：用户通过 Web 浏览器或 LangChain SDK 与 LangSmith 交互。所有流量首先终止于 [Azure 负载均衡器](https://azure.microsoft.com/en-us/products/load-balancer/)，然后被路由到 [AKS](https://azure.microsoft.com/en-us/products/kubernetes-service/) 集群内的前端（NGINX），并在必要时再路由到集群内的其他服务。
- **存储服务**：该平台需要持久化存储用于跟踪记录（traces）、元数据和缓存。在 Azure 上，推荐的服务包括：
    - <Icon icon="database" /> **[Azure Database for PostgreSQL (灵活服务器)](https://azure.microsoft.com/en-us/products/postgresql/)** 用于事务性数据（例如，运行记录、项目）。Azure 的高可用性选项会在另一个区域中部署一个备用副本；数据会同步提交到主服务器和备用服务器。LangSmith 要求使用 PostgreSQL 版本 14 或更高版本。
    - <Icon icon="database" /> **[Azure 托管 Redis](https://azure.microsoft.com/en-us/products/managed-redis/)** 用于队列和缓存。最佳实践包括存储小数值、将大对象拆分成多个 Key、使用管道（pipelining）来最大化吞吐量，并确保客户端和服务器位于同一区域。您也可以使用 [Azure Cache for Redis](https://azure.microsoft.com/en-us/products/cache)，以单实例模式或集群模式运行。LangSmith 要求使用 Redis OSS 版本 5 或更高版本。
    - <Icon icon="chart-line" /> **ClickHouse** 用于高容量的跟踪记录分析。我们建议使用[外部托管的 ClickHouse 解决方案](/langsmith/self-host-external-clickhouse)。如果由于安全或合规性原因不可行，请使用开源 Operator 在 AKS 上部署 ClickHouse 集群。确保数据跨 [可用区 (Availability Zones)](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview) 复制以保证持久性。混合部署不需要 ClickHouse。
    - <Icon icon="cube" /> **[Azure Blob 存储](https://azure.microsoft.com/en-us/products/storage/blobs/)** 用于大型构件（artifacts）。使用冗余存储配置，如读访问地理冗余 (RA-GRS) 或地理区域冗余 (RA-GZRS) 存储，并设计应用程序以便在发生中断时能从辅助区域读取数据。

## Azure 上的计算与网络

### Azure Kubernetes 服务 (AKS)

[AKS](https://azure.microsoft.com/en-us/products/kubernetes-service/) 是生产部署推荐的计算平台。本节概述了规划设置时的关键考虑因素。

#### 网络模型

生产集群请使用 [Azure CNI](https://learn.microsoft.com/en-us/azure/aks/configure-azure-cni) 网络功能。该模型将集群集成到现有的虚拟网络中，为每个 Pod 和节点分配 IP 地址，并允许直接连接到本地或其他 Azure 服务。请确保子网具有足够的 IP 地址用于节点和 Pod，避免地址范围重叠，并为横向扩展事件分配额外的 IP 空间。

#### Ingress 和负载均衡

使用 Kubernetes Ingress 资源和控制器来分发 HTTP/HTTPS 流量。Ingress 控制器在第 7 层（Layer 7）运行，可以根据 URL 路径路由流量并处理 TLS 终止。与第 4 层负载均衡器相比，它们可以减少公共 IP 地址的数量。使用 [应用路由附加组件 (application routing add-on)](https://learn.microsoft.com/en-us/azure/aks/app-routing)，该组件集成了 [Azure DNS](https://azure.microsoft.com/en-us/products/dns/) 和 [Key Vault](https://azure.microsoft.com/en-us/products/key-vault/) 来管理 NGINX Ingress 控制器和 SSL 证书。

#### Web 应用程序防火墙 (WAF)

为了增加对攻击的保护，请部署如 [Azure Application Gateway](https://azure.microsoft.com/en-us/products/application-gateway/) 这样的 [WAF](https://learn.microsoft.com/en-us/azure/web-application-firewall/overview)。WAF 会使用 OWASP 规则过滤流量，并可以在流量到达 AKS 集群之前终止 TLS 连接。

#### 网络策略

应用 [Kubernetes 网络策略](https://learn.microsoft.com/en-us/azure/aks/use-network-policies) 来限制 Pod 间的通信，从而减少受感染工作负载带来的影响。在创建集群时启用网络策略支持，并根据应用程序连接性设计规则。

#### 高可用性

将节点池配置到跨越 [可用区 (availability zones)](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview)，并为所有部署使用 Pod 驱逐预算 (PDB) 和多个副本。设置 Pod 资源请求和限制；[AKS 资源管理最佳实践](https://learn.microsoft.com/en-us/azure/aks/developer-best-practices-resource-management) 建议设置 CPU 和内存限制，以防止 Pod 耗尽所有资源。使用 [集群自动伸缩器 (Cluster Autoscaler)](https://learn.microsoft.com/en-us/azure/aks/cluster-autoscaler) 和 [垂直 Pod 自动伸缩器 (Vertical Pod Autoscaler)](https://learn.microsoft.com/en-us/azure/aks/vertical-pod-autoscaler) 来自动伸缩节点池和调整 Pod 资源。

### 网络和身份

#### 虚拟网络集成

将 AKS 部署到其专属的 [虚拟网络 (virtual network)](https://azure.microsoft.com/en-us/products/virtual-network/) 中，并为集群、数据库、Redis 和存储端点创建单独的子网。使用 [Private Link](https://azure.microsoft.com/en-us/products/private-link/) 和 [服务终结点 (service endpoints)](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview) 将流量保留在您的虚拟网络内部，避免暴露于公共互联网。

#### 身份验证

将 LangSmith 与 [Microsoft Entra ID](https://www.microsoft.com/en-us/security/business/identity-access/microsoft-entra-id)（原 Azure AD）集成，以实现单点登录。使用 Azure AD OAuth2 来获取持有者令牌（bearer tokens），并分配角色以控制对 UI 和 API 的访问。

## 存储和数据服务

### Azure Database for PostgreSQL

#### 高可用性

在启用高可用性模式的 [灵活服务器 (Flexible Server)](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/overview) 上运行。Azure 会在同一可用区（区域性，zonal）或跨可用区（区域冗余，zone-redundant）中配置一个备用副本。数据会同步提交到主服务器和备用服务器，确保已提交的数据不会丢失。区域冗余配置会将备用服务器放置在不同的区域中，以防范区域性中断，但这可能会增加写入延迟。

#### 备份和灾难恢复

启用 [自动备份](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-backup-restore)，并配置地理冗余备份存储以防御区域性故障。对于关键应用程序，请在辅助区域中创建只读副本（read replicas）。

#### 扩展性

选择与您的工作负载匹配的适当 SKU；灵活服务器允许独立扩展计算和存储资源。通过 [Azure Monitor](https://azure.microsoft.com/en-us/products/monitor/) 监控指标并配置警报。

### Azure 托管 Redis

#### 持久性和冗余

选择提供复制和持久性的层级。配置 Redis 持久性或数据备份以确保数据持久性。对于高可用性，请根据所选层级使用 [活动地理复制 (active geo-replication)](https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication) 或区域冗余缓存。

### Azure 上的 ClickHouse

ClickHouse 用于分析工作负载（跟踪记录和反馈）。如果您无法使用外部托管解决方案，请使用 Helm 或官方 Operator 在 AKS 上部署 ClickHouse 集群。为了提高弹性，请确保数据在节点和可用区之间复制。考虑使用 [Azure 磁盘 (Azure Disks)](https://azure.microsoft.com/en-us/products/storage/disks/) 作为本地存储，并将其挂载到 StatefulSets 中。

### Azure Blob 存储

#### 冗余

根据您的恢复目标选择冗余配置。使用 [读访问地理冗余 (RA-GRS) 或地理区域冗余 (RA-GZRS) 存储](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy)，并设计应用程序以便在主区域发生中断时将读取操作切换到辅助区域。

#### 命名和分区

使用有助于跨分区进行负载均衡的命名约定，并规划最大并发客户端数量。请遵守 Azure 的扩展性和容量目标，如果需要，请将数据分区到多个存储账户中。

#### 网络

通过 [私有终结点 (private endpoints)](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints) 访问 Blob 存储，或使用 SAS 令牌和 CORS 规则以启用直接客户端访问。

## 安全性和访问控制

### Azure Key Vault

#### 每个应用和环境使用独立的保管库 (Vault)

将数据库连接字符串和 API 密钥等秘密存储在 [Azure Key Vault](https://azure.microsoft.com/en-us/products/key-vault/) 中。为每个应用程序和环境（开发、测试、生产）使用专用的保管库，以限制安全漏洞的影响范围。

#### 访问控制

使用 [RBAC 权限模型](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide) 在保管库范围内分配角色，并限制对所需主体的访问。使用 Private Link 和防火墙限制网络访问。

#### 数据保护和日志记录

启用 [软删除和清除保护 (soft delete and purge protection)](https://learn.microsoft.com/en-us/azure/key-vault/general/soft-delete-overview)，以防止意外删除。开启日志记录，并为 Key Vault 访问事件配置警报。

### 网络安全

#### Ingress 隔离

仅通过 Ingress 控制器或 WAF 暴露前端服务。其他服务应保持内部状态，并通过集群网络进行通信。

#### RBAC 和 Pod 安全性

使用 [Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/) 来控制谁可以部署、修改或读取资源。启用 [Pod 安全性准入 (pod security admission)](https://kubernetes.io/docs/concepts/security/pod-security-admission/) 以强制执行基线、受限或特权配置文件。

#### 秘密管理

使用 [CSI 秘密存储驱动 (CSI Secret Store)](https://learn.microsoft.com/en-us/azure/aks/csi-secrets-store-driver) 将秘密从 Key Vault 挂载到 Pod 中。避免将秘密存储在环境变量或配置文件中。

## 可观测性和监控

配置您的 LangSmith 实例以[导出遥测数据](/langsmith/export-backend)，这样您就可以使用 Azure 的服务对其进行监控。

### Azure Monitor

使用 [Azure Monitor](https://azure.microsoft.com/en-us/products/monitor/) 进行指标、日志和警报。主动监控包括对关键信号（如节点 CPU/内存利用率、Pod 状态和服务延迟）配置警报。当预定义阈值被超过时，Azure Monitor 警报会通知您。

### 托管的 Prometheus 和 Grafana

启用 [Azure Monitor 托管的 Prometheus](https://learn.microsoft.com/en-us/azure/azure-monitor/essentials/prometheus-metrics-overview) 来收集 Kubernetes 指标。将其与 [Grafana 仪表板](https://azure.microsoft.com/en-us/products/managed-grafana/) 结合使用进行可视化。定义服务等级目标 (SLOs) 并相应地配置警报。

### 容器见解 (Container Insights)

安装 [容器见解 (Container Insights)](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/container-insights-overview) 以捕获 AKS 节点和 Pod 的日志和指标。使用 [Azure Log Analytics 工作区](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-overview) 来查询和分析日志。

### 应用程序日志记录

确保 LangSmith 服务将日志输出到 stdout/stderr，并通过 [Fluent Bit](https://fluentbit.io/) 或 Azure Monitor 代理转发这些日志。
