LangSmith Self-Hosted 允许启用跟踪（traces）的自动 TTL（Time-To-Live，生存时间）和数据保留策略。如果您需要遵守数据隐私法规，或者希望提高空间利用率并自动清理跟踪数据，这将非常有用。此外，跟踪数据的保留期限会根据某些操作或运行规则的应用自动延长。

## 前提条件

您可以通过 Helm 或环境变量设置来配置保留策略。以下是几个可配置的选项：

- *Enabled（启用）:* 数据保留是启用还是禁用。如果启用，您可以通过 UI 设置默认的组织和项目 TTL 层级来应用于跟踪（详情请参阅 [数据保留指南](/langsmith/administration-overview#data-retention)）。
- *Retention Periods（保留期）:* 您可以为短期（shortlived）和长期（longlived）跟踪配置系统范围的保留周期。配置后，您可以在每个项目级别管理保留级别，并为新项目设置组织范围的默认值。

<CodeGroup>

```yaml Helm
config:
  ttl:
    enabled: true
    ttl_period_seconds:
      # -- 400 天长期和 14 天短期
      longlived: "34560000"
      shortlived: "1209600"
```

```bash Docker
# 在您的 .env 文件中
FF_TRACE_TIERS_ENABLED=true
TRACE_TIER_TTL_DURATION_SEC_MAP='{"longlived": 34560000, "shortlived": 1209600}'
```

</CodeGroup>

## ClickHouse TTL 清理作业

从 **0.11** 版本开始，会有一个在周末运行的 cron 作业，用于协助删除 ClickHouse 内置 TTL 机制可能未能清理到位的过期数据。

<Warning>
此作业会使用潜在的长时间运行的**变更操作 (mutations)**（即 `ALTER TABLE DELETE`），这些操作成本较高，可能会影响 ClickHouse 的性能。我们建议仅在非高峰时段（夜间和周末）运行这些操作。在测试中，使用 **1 个并发活动**变更（默认值），我们未观察到显著的 CPU、内存或延迟增加。
</Warning>

### 默认调度

默认情况下，清理作业的运行时间如下：

- **周六**: 协调世界时 (UTC) 20:00 和 22:00
- **周日**: 协调世界时 (UTC) 00:00、02:00 和 04:00

### 禁用作业

要完全禁用清理作业：

```yaml
queue:
  deployment:
    extraEnv:
      - name: "ENABLE_CLICKHOUSE_TTL_CLEANUP_CRON"
        value: "false"
```
### 配置调度
您可以通过修改 cron 表达式来自定义清理作业的运行时间：
```yaml
queue:
  deployment:
    extraEnv:
      # UTC: 周日 00:00/02:00/04:00
      - name: "CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_MORNING"
        value: "0 0,2,4 * * 0"
      # UTC: 周六 20:00/22:00
      - name: "CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_EVENING"
        value: "0 20,22 * * 6"
```
<Tip>
要使作业在单一的 cron 计划下运行，请将 `CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_EVENING` 和 `CLICKHOUSE_TTL_CLEANUP_CRON_WEEKEND_MORNING` 设置为相同的值。作业锁定机制会防止执行重叠。
</Tip>

### 配置每个数据块中的最小过期行数

该作业会逐个表地扫描数据块（parts），并从包含最少过期行数的数据块中删除数据。此阈值用于平衡效率和彻底性：

- **过低**: 作业会扫描整个数据块来清除少量数据（效率低下）
- **过高**: 作业会错过那些包含大量过期数据的数据块

```yaml
queue:
  deployment:
    extraEnv:
      - name: "CLICKHOUSE_TTL_CRON_MIN_EXPIRED_ROWS_PER_PART"
        value: "100000" # 10万行过期数据
```

#### 检查过期行数
使用以下查询来分析表中过期的数据行数，并相应地调整您的最小值：

```sql
-- runs 表的查询。对于其他表，请将 'ttl_seconds' 替换为 'trace_ttl_seconds'
SELECT
    _part,
    count() AS expired_rows
FROM runs
WHERE trace_first_received_at IS NOT NULL
AND ttl_seconds IS NOT NULL
AND toDateTime(assumeNotNull(trace_first_received_at) + toIntervalSecond(assumeNotNull(ttl_seconds))) < now()
GROUP BY _part
ORDER BY expired_rows DESC
```

### 配置最大活动变更数 (Maximum Active Mutations)
删除操作可能非常耗时（处理 100GB 数据块可能需要约 50 分钟）。您可以增加并发的变更数来加快过程：

```yaml
queue:
  deployment:
    extraEnv:
      - name: "CLICKHOUSE_TTL_CRON_MAX_ACTIVE_MUTATIONS"
        value: "1"
```

<Warning>
增加并发的 DELETE 操作可能会严重影响系统性能。请仔细监控您的系统，只有在您能容忍可能较慢的插入和读取延迟时，才增加此值。
</Warning>

### 紧急情况：停止正在运行的变更 (Mutations)

如果您遇到延迟尖峰并需要终止正在运行的变更操作：

1. **查找活动中的变更**:

   ```sql
   SELECT * FROM system.mutations WHERE is_done = 0;
   ```

   查找 `command` 列包含 `DELETE` 语句的 `mutation_id`。

2. **终止变更**:
   ```sql
   KILL MUTATION WHERE mutation_id = '<mutation_id>';
   ```

### 备份与数据保留

如果在运行此作业后磁盘空间没有减少，或者仍在增加，问题可能是备份正在创建文件系统硬链接。这些链接会阻止 ClickHouse 清理数据。

要验证这一点，请检查您的 ClickHouse Pod 内部的以下目录：

 - `/var/lib/clickhouse/backup`
 - `/var/lib/clickhouse/shadow`

如果存在备份文件，请将它们复制到外部文件系统或对象存储（例如 S3），然后清空这些目录。几分钟内，您将看到磁盘空间被释放。
