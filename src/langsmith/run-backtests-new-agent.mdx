部署应用程序只是持续改进过程的开始。在部署到生产环境后，您会希望通过改进提示词（prompts）、语言模型（language models）、工具（tools）和架构（architectures）来完善您的系统。回测（Backtesting）涉及使用历史数据来评估应用程序的新版本，并将新输出与原始输出进行比较。与使用预生产数据集进行的评估相比，回测能更清晰地表明应用程序的新版本是否比当前部署有所改进。

以下是回测的基本步骤：

1. 从您的生产追踪（production tracing）项目中选择样本运行（sample runs）进行测试。
2. 将运行输入（run inputs）转换为数据集，并将运行输出（run outputs）记录为针对该数据集的初始实验。
3. 在新数据集上执行您的新系统，并比较实验结果。

此过程将为您提供一组具有代表性的新数据集，您可以对其进行版本控制，并用于回测您的模型。

<Info>
通常，您可能无法获得明确的“地面真相”（ground truth）答案。在这种情况下，您可以手动标记输出，或者使用不依赖参考数据的评估器（evaluators）。如果您的应用程序允许捕获地面真相标签（例如，通过允许用户留下反馈），我们强烈建议您这样做。
</Info>

import getpass
import os

# 设置项目名称，即您希望进行测试的任何项目
project_name = "Tweet Writing Task"

    os.environ["LANGSMITH_API_KEY"] = getpass.getpass("您的 API KEY")

### 定义应用程序

在此示例中，我们创建一个简单的推文写作应用程序，该应用程序可以访问一些互联网搜索工具：

```python
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain_community.tools import DuckDuckGoSearchRun, TavilySearchResults
from langchain_core.rate_limiters import InMemoryRateLimiter


# 我们将使用 GPT-3.5 Turbo 作为基线，并与 GPT-4o 进行比较
gpt_3_5_turbo = init_chat_model(
    "gpt-3.5-turbo",
    temperature=1,
    configurable_fields=("model", "model_provider"),
)

# 指令作为系统消息传递给 Agent
instructions = """你是一名推文写作助手。给定一个主题，进行一些研究，并就该主题撰写一条相关且引人注目的推文。
- 每条推文至少使用 3 个表情符号
- 推文长度不得超过 280 个字符
- 始终使用搜索工具收集有关推文主题的最新信息
- 仅根据搜索内容撰写推文。不要依赖您的内部知识
- 适当时，链接到您的来源
- 使您的推文尽可能引人注目"""

# 定义 Agent 可以使用的工具
# 如果您的 Tavily API 计划等级更高，可以增加此值
rate_limiter = InMemoryRateLimiter(requests_per_second=0.08)

# 如果您没有 Tavily API 密钥，请使用 DuckDuckGo:
# tools = [DuckDuckGoSearchRun(rate_limiter=rate_limiter)]
tools = [TavilySearchResults(max_results=5, rate_limiter=rate_limiter)]

agent = create_agent(gpt_3_5_turbo, tools=tools, system_prompt=instructions)
```

## 将生产追踪转换为实验

第一步是根据生产*输入*生成数据集，然后复制所有追踪以作为基线实验。

### 选择用于回测的运行

您可以使用 `list_runs` 的 `filter` 参数来选择用于回测的运行。`filter` 参数使用 LangSmith [追踪查询语法](/langsmith/trace-query-syntax)来选择运行。

```python
from datetime import datetime, timedelta, timezone
from uuid import uuid4
from langsmith import Client
from langsmith.beta import convert_runs_to_test

# 获取我们想要转换为数据集/实验的运行
client = Client()

# 我们如何采样要包含在数据集中的运行
end_time = datetime.now(tz=timezone.utc)
start_time = end_time - timedelta(days=1)
run_filter = f'and(gt(start_time, "{start_time.isoformat()}"), lt(end_time, "{end_time.isoformat()}"))'
prod_runs = list(
    client.list_runs(
        project_name=project_name,
        is_root=True,
        filter=run_filter,
    )
)
```

### 将运行转换为实验

`convert_runs_to_test` 是一个函数，它接受一些运行并执行以下操作：

1. 将输入，以及可选的输出，保存到数据集中作为示例（Examples）。
2. 将输入和输出存储为实验，就像您运行了 `evaluate` 函数并收到了这些输出一样。

```python
# 我们想要创建的数据集的名称
dataset_name = f'{project_name}-backtesting {start_time.strftime("%Y-%m-%d")}-{end_time.strftime("%Y-%m-%d")}'
# 从历史运行创建实验的名称
baseline_experiment_name = f"prod-baseline-gpt-3.5-turbo-{str(uuid4())[:4]}"

# 这会将运行转换为数据集 + 实验
convert_runs_to_test(
    prod_runs,
    # 结果数据集的名称
    dataset_name=dataset_name,
    # 是否包含运行输出作为参考/地面真相
    include_outputs=False,
    # 是否在结果实验中包含完整的追踪（默认为仅包含根运行）
    load_child_runs=True,
    # 实验的名称，以便我们之后可以应用评估器
    test_project_name=baseline_experiment_name
)
```

## 使用新系统进行基准测试

现在我们可以开始对新系统进行基准测试，以与我们的生产运行进行比较。

### 定义评估器

首先，我们定义将用于比较这两个系统的评估器。请注意，我们没有任何参考输出，因此我们需要设计仅需要实际输出的评估指标。

```python
import emoji
from pydantic import BaseModel, Field
from langchain_core.messages import convert_to_openai_messages

class Grade(BaseModel):
    """判断一个响应是否被某些上下文所支持的评分。"""
    grounded: bool = Field(..., description="响应的大部分内容是否由检索到的上下文所支持？")

grounded_instructions = f"""你已经提供了一些上下文信息，并要求某人根据该上下文写一个陈述。

请对他们的回应是否完全由您提供的上下文所支持进行评分。\
如果他们陈述中的任何有意义的部分没有直接被您提供的上下文所支持，那么他们的回应就不是基于上下文的（not grounded）。\
否则就是基于上下文的（grounded）。"""
grounded_model = init_chat_model(model="gpt-4o").with_structured_output(Grade)

def lt_280_chars(outputs: dict) -> bool:
    messages = convert_to_openai_messages(outputs["messages"])
    return len(messages[-1]['content']) <= 280

def gte_3_emojis(outputs: dict) -> bool:
    messages = convert_to_openai_messages(outputs["messages"])
    return len(emoji.emoji_list(messages[-1]['content'])) >= 3

async def is_grounded(outputs: dict) -> bool:
    context = ""
    messages = convert_to_openai_messages(outputs["messages"])
    for message in messages:
        if message["role"] == "tool":
            # 工具消息输出是 Tavily/DuckDuckGo 工具返回的结果
            context += "\n\n" + message["content"]
    tweet = messages[-1]["content"]
    user = f"""提供的上下文:
    {context}

    给出的回应:
    {tweet}"""
    grade = await grounded_model.ainvoke([
        {"role": "system", "content": grounded_instructions},
        {"role": "user", "content": user}
    ])
    return grade.grounded
```

### 评估基线

现在，让我们针对基线实验运行我们的评估器。

```python
baseline_results = await client.aevaluate(
    baseline_experiment_name,
    evaluators=[lt_280_chars, gte_3_emojis, is_grounded],
)
# 如果安装了 pandas，可以轻松地将结果探索为 df:
# baseline_results.to_pandas()
```

### 定义并评估新系统

现在，我们来定义并评估我们的新系统。在此示例中，我们的新系统与旧系统相同，但它使用 GPT-4o 而不是 GPT-3.5。由于我们将模型配置为可配置的，我们只需更新传递给 Agent 的默认配置即可：

```python
candidate_results = await client.aevaluate(
    agent.with_config(model="gpt-4o"),
    data=dataset_name,
    evaluators=[lt_280_chars, gte_3_emojis, is_grounded],
    experiment_prefix="candidate-gpt-4o",
)
# 如果安装了 pandas，可以轻松地将结果探索为 df:
# candidate_results.to_pandas()
```

## 比较结果

运行完两个实验后，您可以在数据集中查看它们：

![](/langsmith/images/dataset-page.png)

结果揭示了两个模型之间有趣的权衡：

1. GPT-4o 在遵循格式规则方面表现出改进的性能，一致地包含所需数量的表情符号。
2. 然而，GPT-4o 在保持“基于上下文”（grounded）方面不太可靠。

为了说明基于上下文的问题：在[这个示例运行](https://smith.langchain.com/public/be060e19-0bc0-4798-94f5-c3d35719a5f6/r/07d43e7a-8632-479d-ae28-c7eac6e54da4)中，GPT-4o 包含了关于阿布·巴克尔·穆罕默德·伊本·扎卡里亚·拉齐（Abū Bakr Muhammad ibn Zakariyyā al-Rāzī）在医学贡献方面的事实，这些事实并不存在于搜索结果中。这证明了它正在调用其内部知识，而不是严格使用提供的信息。

这次回测练习表明，虽然 GPT-4o 通常被认为是一个能力更强的模型，但仅仅升级到它并不能改善我们的推文撰写器。要有效地使用 GPT-4o，我们需要：

* 改进我们的提示词，更强烈地强调仅使用提供的信息
* 或者修改我们的系统架构，以更好地约束模型的输出

这个见解展示了回测的价值——它帮助我们在部署前识别了潜在问题。
