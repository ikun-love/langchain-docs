我们非常欢迎代码贡献！无论是修复 Bug、添加新功能还是改进性能，您的贡献都将为成千上万的开发者带来更好的开发体验。

## 开始指南

<Note>
    在提交大型**新功能或重构**之前，请先在 [论坛](https://forum.langchain.com/) 中讨论您的想法。这可以确保与项目目标保持一致，并避免重复工作。

    但这不适用于 Bug 修复或小型改进，这些可以直接通过 Pull Request (PR) 提交。请参阅下面的快速入门指南。
</Note>

### 快速修复：提交 Bug 修复

对于简单的 Bug 修复，您可以立即开始：

<Steps>
    <Step title="重现问题">
        创建一个最小化的测试用例，以演示该 Bug。维护者和其他贡献者应当能够在无需额外设置或修改的情况下运行此测试并观察到失败。
    </Step>

    <Step title="Fork 仓库">
        :::python
        Fork [LangChain](https://github.com/langchain-ai/langchain) 或 [LangGraph](https://github.com/langchain-ai/langchain) 仓库到您的 <Tooltip tip="如果您将仓库 Fork 到组织账户下，维护者将无法进行编辑。">个人 GitHub 账户</Tooltip>
        :::
        :::js
        Fork [LangChain](https://github.com/langchain-ai/langchainjs) 或 [LangGraph](https://github.com/langchain-ai/langgraphjs) 仓库到您的个人 GitHub 账户
        :::
    </Step>

    <Step title="克隆并设置">
        :::python

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 以 LangChain 为例：
        git clone https://github.com/parrot123/langchain.git

        # 对于 LangGraph：
        git clone https://github.com/parrot123/langgraph.git
        ```

        ```bash
        # 在您的仓库内，安装依赖项
        uv sync --all-groups
        ```

        如果您之前没有安装过 [`uv`](https://docs.astral.sh/uv/)，则需要先安装它
        :::
        :::js

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 以 LangChain 为例：
        git clone https://github.com/parrot123/langchainjs.git

        # 对于 LangGraph：
        git clone https://github.com/parrot123/langgraphjs.git
        ```

        ```bash
        # 在您的仓库内，安装依赖项
        pnpm install
        # 为所有包创建一个构建，以解析工作区依赖项
        pnpm build
        ```
        :::
    </Step>

    <Step title="创建分支">
        为您的修复创建一个新的分支。这有助于整理您的更改，并使稍后提交 PR 更加容易。

        ```bash
        git checkout -b your-username/short-bugfix-name
        ```
    </Step>

    <Step title="编写失败的测试">
        添加 [单元测试](#test-writing-guidelines)，该测试在没有您的修复时会失败。这使我们能够验证 Bug 是否已解决，并防止回归。
    </Step>

    <Step title="进行修改">
        在修复 Bug 的同时，请遵循我们的 [代码质量标准](#code-quality-standards)。进行**解决问题所需的最小化更改**
    </Step>

    :::js
    <Step title="运行构建">
        运行构建命令以确保包仍然可以正常构建
        ```bash
        pnpm build
        # 或构建特定的工作区包
        pnpm --filter @langchain/core build
        ```
    </Step>
    :::

    <Step title="验证修复">
        确保测试通过且没有引入回归。在提交 PR 之前，确保所有测试在本地均已通过。

        :::python

        ```bash
        make lint
        make test

        # 对于涉及集成的 Bug 修复，还需运行：
        make integration_tests
        # （您可能需要设置 API 测试凭证）
        ```
        :::
        :::js

        ```bash
        pnpm lint
        pnpm test

        # 对于涉及集成的 Bug 修复，还需运行：
        pnpm test:int

        # 或在特定工作区包中运行测试
        cd libs/langchain-core
        pnpm test
        pnpm lint

        # 或从仓库根目录运行特定包的测试
        pnpm --filter @langchain/core test
        pnpm --filter @langchain/core lint
        ```
        :::
    </Step>

    <Step title="记录更改">
        如果行为发生变化，请更新文档字符串（docstrings），并在逻辑复杂的地方添加注释。
    </Step>

    <Step title="提交 Pull Request">
        遵循提供的 PR 模板。如果适用，请使用 [关闭关键字](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)（例如 `Fixes #ISSUE_NUMBER`）引用您正在修复的 Issue，以便在您的 PR 合并时，该 Issue 能自动关闭。
    </Step>
</Steps>

### 全面开发环境设置

## 贡献指南

在开始向 LangChain 做出贡献之前，请花点时间思考您想做出贡献的原因。如果您的唯一目标是为简历添加“第一次贡献”记录（或者您只是想快速赢一次），那么您可能更适合参加训练营或在线教程。

为开源项目做贡献需要时间和精力，但这也可以帮助您成为更好的开发者并学习新技术。然而，重要的是要知道，这可能比遵循培训课程更困难、更慢。尽管如此，如果您愿意花时间把事情做好，为开源做贡献是值得的。

### 向后兼容性

<Warning>
    除非是关键的安全修复，否则不允许对公共 API 进行破坏性更改。

    有关主要版本发布的详细信息，请参阅我们的[版本控制策略](/oss/versioning)。
</Warning>

通过以下方式保持兼容性：

<AccordionGroup>
    <Accordion title="稳定接口">
        **始终保持不变**:
        - 函数签名和参数名称
        - 类接口和方法名称
        - 返回值结构和类型
        - 公共 API 的导入路径
    </Accordion>

    <Accordion title="安全更改">
        **可接受的修改**:
        :::python
        - 添加新的可选参数
        :::
        :::js
        - 添加新的可选参数/类型参数
        :::
        - 向类中添加新方法
        - 在不改变行为的情况下提高性能
        - 添加新的模块或函数
    </Accordion>

    <Accordion title="在进行更改之前">
        - **这会破坏现有用户代码吗？**
        - 检查您的目标是否是公共的
        :::python
        - 如果有需要，它是否在 `__init__.py` 中导出？
        :::
        - 测试中是否存在现有的使用模式？
    </Accordion>
</AccordionGroup>

### 新功能

我们力求为新功能设定较高的标准。通常情况下，除非存在明确的需求，否则我们不接受来自外部贡献者对核心抽象的更改。这也适用于基础设施和依赖项的更改。

通常，功能贡献要求包括：

<Steps>
    <Step title="设计讨论">
        打开一个 Issue，描述：

        - 您正在解决的问题
        - 提议的 API 设计
        - 预期的使用模式
    </Step>

    <Step title="实现">
        - 遵循现有的代码模式
        - 包含全面的测试和文档
        - 考虑安全影响
    </Step>

    <Step title="集成考虑">
        - 此功能如何与现有功能交互？
        - 是否有性能影响？
        - 是否引入了新的依赖项？

        我们将会拒绝那些可能导致安全漏洞或报告的功能。
    </Step>
</Steps>

### 安全指南

<Warning>
    安全性是至高无上的。切勿引入漏洞或不安全模式。
</Warning>

安全清单：

<AccordionGroup>
    <Accordion title="输入验证">
        - 验证和清理所有用户输入
        - 在模板和查询中正确转义数据
        :::python
        - 绝不要对用户数据使用 `eval()`, `exec()`, 或 `pickle`，因为这可能导致任意代码执行漏洞
        :::
        :::js
        - 绝不要使用 `eval()`，因为它可能导致任意代码执行漏洞
        :::
    </Accordion>

    <Accordion title="错误处理">
        - 使用特定的异常类型
        - 不要从错误消息中泄露敏感信息
        - 实现适当的资源清理
    </Accordion>

    <Accordion title="依赖项">
        - 避免添加硬性依赖
        - 保持可选依赖项的最小化
        - 审查第三方包的安全问题
    </Accordion>
</AccordionGroup>

## 开发工作流

### 测试要求

<Info>
    目录路径相对于您正在处理的包。
</Info>

每次代码更改都必须包含全面的测试。

#### 单元测试

:::python
**位置**: `tests/unit_tests/`
:::
:::js
**位置**: `src/tests/FILENAME_BEING_TESTED.test.ts`
:::

**要求**:
- 不允许进行网络调用
- 测试所有代码路径，包括边缘情况
- 对外部依赖项使用 Mock（模拟）

:::python
```bash
make test

# 或直接运行：
uv run --group test pytest tests/unit_tests
```
:::
:::js
```bash
# 运行整个测试套件
pnpm test

# 或运行特定的测试文件
pnpm test src/tests/FILENAME_BEING_TESTED.test.ts

# 或运行特定的测试函数
pnpm test -t "the test that should be run"
```
:::

#### 集成测试

:::python
**位置**: `tests/integration_tests/`
:::
:::js
**位置**: `src/tests/FILENAME_BEING_TESTED.int.test.ts`
:::

集成测试需要访问外部服务/提供程序 API（可能会产生费用），因此默认情况下不会运行。

并非所有代码更改都需要集成测试，但请记住，在我们的审查过程中，我们会将其作为单独的步骤要求/运行集成测试。

**要求**:
- 测试与外部服务的真实集成
- 使用环境变量提供 API 密钥
- 如果凭证不可用，则优雅地跳过

:::python
```bash
make integration_tests
```
:::
:::js
```bash
pnpm test:int
```
:::

### 代码质量标准

贡献内容必须遵守以下质量要求：

<Tabs>
    <Tab title="类型提示">
        :::python
        **要求**: 对所有函数进行完整的类型注解

        ```python
        def process_documents(
            docs: list[Document],
            processor: DocumentProcessor,
            *,
            batch_size: int = 100
        ) -> ProcessingResult:
            """以批次处理文档。

            Args:
                docs: 要处理的文档列表。
                processor: 文档处理实例。
                batch_size: 每批文档的数量。

            Returns:
                包含成功/失败计数的处理结果。
            """
        ```
        :::
        :::js
        **要求**: 所有导出函数和接口都应具有完整的类型

        ```typescript
        /**
         * 文档处理实例。
         */
        interface FooDocumentProcessor {
            /**
             * 以批次处理文档。
             *
             * @param docs - 要处理的文档列表。
             * @returns 包含成功/失败计数的处理结果。
             */
            process(docs: Document[]): ProcessingResult;
        }

        /**
         * 以批次处理文档。
         *
         * @param docs - 要处理的文档列表。
         * @param processor - 文档处理实例。
         * @param batchSize - 每批文档的数量。
         * @returns 包含成功/失败计数的处理结果。
         */
        export function processDocuments(
            docs: Document[],
            processor: DocumentProcessor,
            batchSize: number = 100
        ): ProcessingResult {
            // ...
        }
        ```
        :::
    </Tab>

    <Tab title="文档">
        :::python
        **要求**: 所有公共函数都使用 [Google 风格的文档字符串](https://google.github.io/styleguide/pyguide.html#docstrings)。

        **指导原则**: 文档字符串描述“做的事情”；本网站上的文档解释“如何做”和“为什么”。

        | 内容类型 | 位置 | 目的 |
        |---|---|---|
        | 参数描述 | 文档字符串 | 自动生成到 API 参考中 |
        | 返回类型和异常 | 文档字符串 | API 参考 |
        | 最小使用示例 | 文档字符串 | 展示基本实例化模式 |
        | 功能教程 | 本网站 | 深入的演练 |
        | 端到端示例 | 本网站 | 真实世界的使用模式 |
        | 概念解释 | 本网站 | 理解和上下文 |

        **文档字符串应包含**:

        1. 关于类/函数作用的一行摘要
        2. 指向本网站以获取教程、指南和使用模式的链接
        3. 包含类型和描述的参数文档
        4. 返回值描述
        5. 可能被引发的异常
        6. 必要时，包含一个展示基本实例化/使用情况的最小示例

        <AccordionGroup>
            <Accordion title="良好的文档字符串示例">
                ````python
                class ChatAnthropic(BaseChatModel):
                ````
