完善的文档是 LangChain 不可或缺的一部分。我们欢迎为新功能和 [集成（Integrations）](/oss/contributing/publish-langchain#adding-documentation) 贡献文档，同时也欢迎对现有文档进行社区改进。

<Note>
    这些是针对我们开源项目的贡献指南，但它们同样适用于 [LangSmith 文档](/langsmith/home)。
</Note>

## 贡献

### 快速编辑

对于修复拼写错误或更改链接这类快速修改，你无需设置本地开发环境，可以直接在 GitHub 上进行编辑：

<Info>
    **前提条件：**
    - 一个 [GitHub](https://github.com/) 账户
    - 对贡献的 [Fork 与 Pull Request 工作流程](https://graphite.dev/guides/understanding-git-fork-pull-request-workflow) 有基本的了解
</Info>

1. 在你想要编辑的页面底部，点击链接 **在 GitHub 上编辑此页面的源文件 (Edit the source of this page on GitHub)**。
1. GitHub 会提示你将仓库 Fork 到你的账户下。请确保是 Fork 到你的<Tooltip tip="如果克隆到组织（Organization）下，维护者将无法进行编辑，这可能会延迟 PR 的采纳。">个人账户</Tooltip>中。
1. 直接在 GitHub 的网页编辑器中进行更改。
1. 点击 **Commit changes...** 并给你的提交一个描述性的标题，例如 `fix(docs): summary of change`。如果适用，可以添加一个[扩展描述](https://www.gitkraken.com/learn/git/best-practices/git-commit-message#git-commit-message-structure)。
1. GitHub 会引导你创建一个 Pull Request (PR)。为其设置一个标题（通常与提交信息相同），并遵循 PR 模板中的清单。

<Note>
    通常文档 PR 会在几天内被审核。请留意你的 PR 动态，以便根据维护者的反馈进行修改。

    除非你有新的信息要提供，否则请勿“顶起” (bump) PR——维护者会根据他们的空闲时间来处理。
</Note>

### 较大的编辑和新增内容

对于较大规模的更改、内容新增或持续贡献，需要在本地机器上设置开发环境。我们的文档构建流程支持本地预览，这对于确保您所做的更改在提交前按预期显示非常重要。

#### 设置本地环境

在你可以开始参与本项目之前，请确保已安装以下组件：

**必需组件：**

- `python >= 3.13, < 4.0`
- [**`uv`**](https://docs.astral.sh/uv/) - Python 包管理器（用于依赖管理）
- [**Node.js**](https://nodejs.org/en) 和 [**`npm`**](https://www.npmjs.com/) - 用于 Mintlify CLI 和参考文档的构建
- [**Make**](https://www.gnu.org/software/make/) - 用于运行构建命令
- [**Git**](https://git-scm.com/) - 用于版本控制

**可选但推荐：**

- **[`markdownlint-cli`](https://github.com/igorshubovych/markdownlint-cli)** - 用于 Markdown 文件检查 (Linting)

    ```bash
    npm install -g markdownlint-cli
    ```
- **[`pnpm`](https://pnpm.io/)** - 仅在处理参考文档时需要

    ```bash
    npm install -g pnpm@10.14.0
    ```

- [**Mintlify MDX VSCode 扩展**](https://www.mintlify.com/blog/mdx-vscode-extension)

**设置步骤：**

1. 克隆 [`langchain-ai/docs`](https://github.com/langchain-ai/docs) 仓库。请遵循 [`IDE_SETUP.md`](https://github.com/langchain-ai/docs/blob/main/IDE_SETUP.md) 中概述的步骤。

2. 安装依赖项：

    ```bash
    make install
    ```

    此命令将执行以下操作：
    - 使用 `uv sync --all-groups` 安装 Python 依赖项
    - 通过 npm 全局安装 Mintlify CLI

3. 验证设置：

    ```bash
    make build
    ```

    这应该能在没有错误的情况下构建文档。

安装完成后，你就可以使用 `docs` 命令了：

```bash
docs --help
```

常用命令：

* `docs dev` - 启动开发模式，支持文件监听和热重载
* `docs build` - 构建文档

有关更多详细信息，请参阅 [可用命令](#available-commands) 部分。

#### 编辑文档

<Note>
    **只编辑 `src/` 目录下的文件**——`build/` 目录是自动生成的。
</Note>

1. 确保你的[环境已设置好](#set-up-local-environment)，并且你已按照 [`IDE_SETUP.md`](https://github.com/langchain-ai/docs/blob/main/IDE_SETUP.md) 中的步骤配置了你的 IDE/编辑器以自动应用正确的设置。

1. 编辑 `src/` 目录下的文件
   * 对 Markdown 文件进行更改，构建系统将自动检测更改并重新构建受影响的文件。
   * 如果某一功能的 OSS 内容在 Python 和 JavaScript/TypeScript 之间存在差异，请[在同一个文件中为两者都添加内容](#co-locate-python-and-javascripttypescript-oss-content)。否则，内容在两种语言的版本中将保持一致。
   * 使用 [Mintlify 语法](https://mintlify.com/docs) 进行格式化。

1. 启动开发模式以在本地预览更改：

    ```bash
    docs dev
    ```

    这将在 `http://localhost:3000` 启动一个带热重载的开发服务器。

1. 迭代

   * 持续编辑并立即查看更改结果。
   * 开发服务器只重建更改过的文件，以提供更快的反馈速度。

1. 运行[质量检查](#run-quality-checks)，以确保你的更改有效。
1. 获得相关审核者的批准。

    LangChain 团队成员可以[创建可共享的预览构建](#create-a-sharable-preview-build)

1. [发布到生产环境](#publish-to-prod)（仅限团队成员）。

#### 创建可共享的预览构建

<Note>
    只有 LangChain 团队成员可以创建可共享的预览构建。
</Note>

<Accordion
    title="说明"
>
    预览对于与他人共享进行中的工作很有用。

    当你创建或更新一个 PR 时，会自动为你生成一个[预览分支/ID](https://github.com/langchain-ai/docs/actions/workflows/create-preview-branch.yml)。PR 中会留下一个包含该 ID 的评论，你可以使用该 ID 来生成预览。（如果需要，你也可以手动运行此工作流。）

    1. 从评论中复制预览分支的 ID。
    1. 在 [Mintlify 仪表板](https://dashboard.mintlify.com/langchain-5e9cc07a/langchain-5e9cc07a?section=previews)上，点击 **Create preview deployment** (创建预览部署)。
    1. 输入预览分支的 ID。
    1. 点击 **Create deployment** (创建部署)。
        在 **Previews** (预览) 表中将显示一个 **Manual update** (手动更新)。
    1. 选择该预览并点击 **Visit** (访问) 查看预览构建。

    若要使用最新更改重新部署预览构建，请在 Mintlify 仪表板上点击 **Redeploy**（重新部署）。
</Accordion>

#### 运行质量检查

在提交更改之前，请确保你的代码通过了格式化和检查（linting）测试：

```bash
# 检查损坏的链接
make mint-broken-links

# 自动格式化代码
make format

# 检查是否存在 Linter 问题
make lint

# 修复 Markdown 问题
make lint_md_fix

# 运行测试以确保你的更改不会破坏现有功能
make test
```

有关更多详细信息，请参阅 `README` 中[可用命令](#available-commands)部分。

<Important>
    所有 Pull Requests 都会自动由 CI/CD 进行检查。相同的 Linter 和格式化标准将被强制执行，如果这些检查失败，PR 将无法合并。
</Important>

### 操作指南 (How-to guides)

操作指南是为那些知道自己想完成什么任务的用户提供的面向任务的说明。操作指南的示例可以在 [LangChain](/oss/langchain/overview) 和 [LangGraph](/oss/langchain/overview) 标签页上找到。

<AccordionGroup>
    <Accordion title="特点">
        - **面向任务**：专注于特定任务或问题
        - **分步指导**：将任务分解成更小的步骤
        - **实践性强**：提供具体的示例和代码片段
    </Accordion>

    <Accordion title="技巧">
        - 关注**如何做 (how)** 而不是**为什么 (why)**
        - 使用具体的示例和代码片段
        - 将任务分解成更小的步骤
        - 链接到相关的概念指南和参考资料
    </Accordion>

    <Accordion title="示例">
        - [消息 (Messages)](/oss/langchain/messages)
        - [工具 (Tools)](/oss/langchain/tools)
        - [流式处理 (Streaming)](/oss/langgraph/streaming)
    </Accordion>
</AccordionGroup>

### 概念指南 (Conceptual guides)

概念指南抽象地涵盖核心概念，提供深入的理解。

<AccordionGroup>
    <Accordion title="特点">
        - **侧重理解**：解释事物的工作原理
        - **全局视角**：比其他类型的内容更宏观、更全面
        - **设计导向**：解释设计决策和权衡
        - **背景丰富**：使用类比和对比
    </Accordion>

    <Accordion title="技巧">
        - 关注**“为什么 (why)”**而不是“如何做 (how)”
        - 提供不一定需要使用功能本身就必需的补充信息
        - 可以使用类比并引用替代方案
        - 避免混入过多的参考内容
        - 链接到相关的教程和操作指南
    </Accordion>

    <Accordion title="示例">
        - [内存 (Memory)](/oss/concepts/memory)
        - [上下文 (Context)](/oss/concepts/context)
        - [Graph API](/oss/langgraph/graph-api)
        - [Functional API](/oss/langgraph/functional-api)
    </Accordion>
</AccordionGroup>

### 参考 (Reference)

参考文档包含详细的、低层面的信息，准确描述了存在哪些功能以及如何使用它们。

<CardGroup cols={2}>

    <Card title="JavaScript/TypeScript 参考" href="https://reference.langchain.com/javascript/" icon="js" arrow />

一份好的参考文档应该：
- 描述存在的内容（所有参数、选项、返回值）
- 内容详尽且结构化，便于查找
- 作为技术细节的权威来源

<AccordionGroup>
    <Accordion title="为参考文档做贡献">
        :::python
        有关链接到 Python 参考文档的更多信息，请参阅[Python 参考文档贡献指南](https://github.com/langchain-ai/docs/blob/main/reference/python/README.md)。
        :::
        :::js
        有关链接到 JavaScript/TypeScript 参考文档的更多信息，请参阅[JavaScript/TypeScript 参考文档贡献指南](https://github.com/langchain-ai/docs/blob/main/reference/javascript/README.md)。
        :::
    </Accordion>

    <Accordion title="LangChain 参考最佳实践">
        - **保持一致性**；遵循现有模式来编写特定于提供商的文档
        - 包含基本用法（代码片段）和常见边缘情况/失败模式
        - 标明哪些功能需要特定的版本
    </Accordion>

    <Accordion title="何时创建新的参考文档">
        - 新的集成或提供商需要专用的参考页面
        - 复杂的配置选项需要详细解释
        - API 更改引入了新参数或行为时
        - 社区经常询问特定功能时
    </Accordion>
</AccordionGroup>

### 教程 (Tutorials)

教程是篇幅更长的分步指南，它们会逐步深入，引导用户完成特定的实践活动以建立理解。教程通常可以在 [Learn](/oss/learn) 标签页找到。

<Note>
    我们通常不接受来自外部贡献者提交的新教程，除非有迫切需要。如果你觉得文档中缺少某个主题或覆盖不足，请[打开一个新的 Issue](https://github.com/langchain-ai/docs/issues)。
</Note>

<AccordionGroup>
    <Accordion title="特点">
        - **实践性**：专注于通过实践活动建立理解。
        - **分步指导**：将活动分解成更小的步骤。
        - **动手操作**：提供按顺序执行且可运行的代码片段。
        - **补充性**：提供不一定用于特定功能使用所需的额外上下文和信息。
    </Accordion>

    <Accordion title="技巧">
        - 代码片段应是连续的，并且如果用户按顺序操作，它们应该是可运行的。
        - 为活动提供一些背景信息，但针对更详细的信息链接到相关的概念指南和参考资料。
    </Accordion>

    <Accordion title="示例">
        - [语义搜索](/oss/langchain/knowledge-base)
        - [RAG 代理](/oss/langchain/rag)
    </Accordion>
</AccordionGroup>

### Python 和 JavaScript/TypeScript 内容共置

在可能的情况下，所有文档都必须同时使用 Python 和 JavaScript/TypeScript 编写。为此，我们使用自定义的内联语法来区分应出现在一个或两个语言中的内容部分：

```mdx
\:::python
仅 Python 特定的内容。在实际文档中，前面的反斜杠（在 `python` 前）会被省略。
\:::

\:::js
仅 JavaScript/TypeScript 特定的内容。在实际文档中，前面的反斜杠（在 `js` 前）会被省略。
\:::

两个语言都适用的内容（不被包裹）
```

这将生成两个输出（每个语言一个）在 `/oss/python/concepts/foo.mdx` 和 `/oss/javascript/concepts/foo.mdx`。每个输出页面都需要添加到 `/src/docs.json` 文件中才能包含在导航中。

<Note>
    我们不希望缺乏内容对等性成为贡献的障碍。如果某一功能只在一个语言中可用，那么只在该语言中保留文档是可以接受的，直到另一种语言也支持该功能。在这种情况下，请务必包含一个说明该功能在另一种语言中尚不可用的注释。

    如果你在翻译 Python 和 JavaScript/TypeScript 内容之间需要帮助，请在 [社区 Slack 频道](https://www.langchain.com/join-community) 中提问，或在你的 PR 中标记维护者。
</Note>

## 质量标准

### 一般准则

<AccordionGroup>
    <Accordion title="避免重复">
        涵盖相同材料的多个页面难以维护并会引起混淆。每个概念或功能应该只有一个权威页面。应链接到其他指南，而不是重新解释。
    </Accordion>

    <Accordion title="频繁链接">
        文档部分不是孤立存在的。应频繁链接到其他部分，使用户可以了解不熟悉的主题。这包括链接到 API 参考和概念部分。
    </Accordion>

    <Accordion title="保持简洁">
        采取“少即是多”的方法。如果已经存在一个很好的解释部分，请链接到它，而不是重新解释，除非你的内容提出了一个新的视角。
    </Accordion>
</AccordionGroup>

### 可访问性要求

确保文档对所有用户都是可访问的：

- 使用标题和列表来组织内容，以便于快速浏览
- 使用具体、可操作的链接文本，而不是“点击这里”
- 为所有图像和图表包含描述性的替代文本 (alt text)

### 交叉引用

使用一致的交叉引用来连接文档与 API 参考文档。

**从文档链接到 API 参考：**

使用 `@[]` 语法链接到 API 参考页面：

```mdx
See \@[`ChatAnthropic`] for all configuration options.

The \@[`bind_tools`][ChatAnthropic.bind_tools] method accepts...
```

构建管道会根据当前的语言范围（Python 或 JavaScript）将这些转换为适当的 Markdown 链接。例如，`\@[ChatAnthropic]` 会链接到 Python 或 JS API 参考页面，**但前提是 `link_map.py` 文件中必须存在相应的条目！** 详情见下文。

<Accordion title="自动链接的工作原理">

`@[]` 语法由 [`handle_auto_links.py`](https://github.com/langchain-ai/docs/blob/main/pipeline/preprocessors/handle_auto_links.py) 处理。它会在 `link_map.py` 中查找链接键，该文件包含 Python 和 JavaScript 范围的字典映射。

**支持的格式：**

| 语法 | 结果 |
|--------|--------|
| `\@[ChatAnthropic]` | 显示文本为 "ChatAnthropic" 的链接 |
| `` \@[`ChatAnthropic`] `` | 显示文本为 `` `ChatAnthropic` ``（代码格式化）的链接 |
| `\@[text][ChatAnthropic]` | 显示文本为 "text"，链接键为 `ChatAnthropic` (需要在链接映射中定义) |
| `\\@[ChatAnthropic]` | 转义：渲染为字面量 `\@[ChatAnthropic]`（不链接——当前页面正在使用的形式！） |

**添加新链接：**
