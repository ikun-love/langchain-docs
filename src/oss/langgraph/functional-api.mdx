**函数式 API (Functional API)** 允许您以最少的代码更改，将 LangGraph 的核心功能——[持久化](/oss/langgraph/persistence)、[内存](/oss/langgraph/add-memory)、[人工干预 (Human-in-the-Loop, HITL)](/oss/langgraph/interrupts) 和 [流式传输](/oss/langgraph/streaming)——添加到您的应用程序中。

它的设计目标是将这些功能集成到使用标准语言原语（如 `if` 语句、`for` 循环和函数调用）进行分支和控制流的现有代码中。与许多要求将代码重构为显式管道或 DAG（有向无环图）的数据编排框架不同，函数式 API 允许您在不强制执行严格执行模型的情况下整合这些能力。

函数式 API 使用两个关键构建块：

:::python
* **`@entrypoint`** – 将一个函数标记为工作流的起点，负责封装逻辑和管理执行流程，包括处理长时间运行的任务和中断。
* **`@task`** – 代表一个离散的工作单元，例如 API 调用或数据处理步骤，它可以在 `entrypoint` 内部异步执行。任务返回一个类似于 future 的对象，可以被同步等待或异步解析。
:::

:::js
* **`entrypoint`** – 入口点封装了工作流逻辑并管理执行流程，包括处理长时间运行的任务和中断。
* **`task`** – 代表一个离散的工作单元，例如 API 调用或数据处理步骤，它可以在 `entrypoint` 内部异步执行。任务返回一个类似于 future 的对象，可以被同步等待或异步解析。
:::

这为构建带有状态管理和流式传输的工作流提供了一个最小化的抽象层。

<Tip>
有关如何使用函数式 API 的信息，请参阅 [使用函数式 API](/oss/langgraph/use-functional-api)（Use Functional API）。
</Tip>

## 函数式 API 与图 API 对比

对于偏好更具声明性方法的[^1]用户，LangGraph 的 [图 API (Graph API)](/oss/langgraph/graph-api) 允许您使用图范式定义工作流。两个 API 共享相同的底层运行时，因此您可以在同一应用程序中同时使用它们。

以下是它们之间的一些关键区别：

* **控制流**: 函数式 API 不需要您考虑图结构。您可以使用标准的 Python 结构来定义工作流。这通常会减少您需要编写的代码量。
* **短期内存**: **图 API** 要求声明一个 [**State**](/oss/langgraph/graph-api#state)，并且可能需要定义 [**reducers**](/oss/langgraph/graph-api#reducers) 来管理图状态的更新。`@entrypoint` 和 `@tasks` 不需要显式的状态管理，因为它们的状态作用域限定在函数内部，且不在函数间共享。
* **检查点 (Checkpointing)**: 两个 API 都会生成和使用检查点。在 **图 API** 中，每次[超级步骤 (superstep)](/oss/langgraph/graph-api) 后都会生成一个新的检查点。在 **函数式 API** 中，当任务执行时，其结果会保存到与给定入口点关联的现有检查点中，而不是创建新检查点。
* **可视化**: 图 API 可以方便地将工作流可视化为图形，这对于调试、理解工作流和与他人共享非常有用。函数式 API 不支持可视化，因为图是在运行时动态生成的。

## 示例

下面我们演示一个简单的应用程序，该程序会撰写一篇文章，然后 [暂停](/oss/langgraph/interrupts) 以请求人工审核。

:::python
```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task
from langgraph.types import interrupt

@task
def write_essay(topic: str) -> str:
    """根据给定主题撰写一篇文章。"""
    time.sleep(1) # 这是一个长时间运行任务的占位符。
    return f"An essay about topic: {topic}"

@entrypoint(checkpointer=InMemorySaver())
def workflow(topic: str) -> dict:
    """一个简单的、会撰写文章并请求审核的工作流。"""
    essay = write_essay("cat").result()
    is_approved = interrupt({
        # 提供给 interrupt 参数的任何 JSON 可序列化负载。
        # 当从工作流流式传输数据时，它会作为 Interrupt（中断）显示在客户端。
        "essay": essay, # 我们希望审核的文章。
        # 我们可以添加任何其他需要的信息。
        # 例如，引入一个名为 "action" 的键，其中包含一些说明。
        "action": "Please approve/reject the essay",
    })

    return {
        "essay": essay, # 生成的文章
        "is_approved": is_approved, # 来自 HITL 的响应
    }
```
:::

:::js
```typescript
import { MemorySaver, entrypoint, task, interrupt } from "@langchain/langgraph";

const writeEssay = task("writeEssay", async (topic: string) => {
  // 这是一个长时间运行任务的占位符。
  await new Promise((resolve) => setTimeout(resolve, 1000));
  return `An essay about topic: ${topic}`;
});

const workflow = entrypoint(
  { checkpointer: new MemorySaver(), name: "workflow" },
  async (topic: string) => {
    const essay = await writeEssay(topic);
    const isApproved = interrupt({
      // 提供给 interrupt 参数的任何 JSON 可序列化负载。
      // 当从工作流流式传输数据时，它会作为 Interrupt（中断）显示在客户端。
      essay, // 我们希望审核的文章。
      // 我们可以添加任何其他需要的信息。
      // 例如，引入一个名为 "action" 的键，其中包含一些说明。
      action: "Please approve/reject the essay",
    });

    return {
      essay, // 生成的文章
      isApproved, // 来自 HITL 的响应
    };
  }
);
```
:::

<Accordion title="详细解释">
  该工作流将撰写一篇关于主题 "cat" 的文章，然后暂停以获取人工审核。工作流可以无限期中断，直到提供审核意见。

  当工作流恢复执行时，它会从头开始执行，但由于 `writeEssay` 任务的结果已保存，因此任务结果将从检查点加载，而不会重新计算。

## 入口点 (Entrypoint)

:::python
使用 `@[`@entrypoint`]` 装饰器可以从一个函数创建工作流。它封装了工作流逻辑并管理执行流程，包括处理_长时间运行的任务_和[中断](/oss/langgraph/interrupts)。
:::

:::js
使用 `[`entrypoint`][entrypoint]` 函数可以从一个函数创建工作流。它封装了工作流逻辑并管理执行流程，包括处理_长时间运行的任务_和[中断](/oss/langgraph/interrupts)。
:::

### 定义

:::python
**入口点**是通过使用 `@entrypoint` 装饰器来定义的。

该函数**必须接受一个位置参数**，该参数作为工作流的输入。如果您需要传递多部分数据，请将字典作为第一个参数的输入类型。

用 `entrypoint` 装饰函数会产生一个 @[`Pregel`][Pregel.stream] 实例，它有助于管理工作流的执行（例如处理流式传输、恢复和检查点）。

您通常希望向 `@entrypoint` 装饰器传递一个**检查点 (checkpointer)** 以启用持久化并使用**人工干预 (human-in-the-loop)** 等特性。

<Tabs>
    <Tab title="同步 (Sync)">
    ```python
    from langgraph.func import entrypoint

    @entrypoint(checkpointer=checkpointer)
    def my_workflow(some_input: dict) -> int:
        # 一些可能涉及长时间运行任务（如 API 调用）的逻辑，
        # 并且可能因人工干预而被中断。
        ...
        return result
    ```
    </Tab>
    <Tab title="异步 (Async)">
    ```python
    from langgraph.func import entrypoint

    @entrypoint(checkpointer=checkpointer)
    async def my_workflow(some_input: dict) -> int:
        # 一些可能涉及长时间运行任务（如 API 调用）的逻辑，
        # 并且可能因人工干预而被中断。
        ...
        return result
    ```
    </Tab>
</Tabs>
:::

:::js
**入口点**是通过向 `entrypoint` 函数提供配置和一个函数来定义的。

该函数**必须接受一个位置参数**，该参数作为工作流的输入。如果您需要传递多部分数据，请将对象作为第一个参数的输入类型。

使用函数创建入口点会产生一个工作流实例，它有助于管理工作流的执行（例如处理流式传输、恢复和检查点）。

您通常希望向 `entrypoint` 函数传递一个**检查点 (checkpointer)** 以启用持久化并使用**人工干预 (human-in-the-loop)** 等特性。

```typescript
import { entrypoint } from "@langchain/langgraph";

const myWorkflow = entrypoint(
  { checkpointer, name: "workflow" },
  async (someInput: Record<string, any>): Promise<number> => {
    // 一些可能涉及长时间运行任务（如 API 调用）的逻辑，
    // 并且可能因人工干预而被中断。
    return result;
  }
);
```
:::

<Warning>
**序列化 (Serialization)**
入口点的**输入**和**输出**必须是 JSON 可序列化的，以支持检查点功能。有关更多详细信息，请参阅[序列化](#serialization)部分。
</Warning>

:::python
### 可注入参数 (Injectable parameters)

在声明 `entrypoint` 时，您可以请求访问将在运行时自动注入的其他参数。这些参数包括：

| 参数 | 描述 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **previous** | 访问给定线程的先前 `checkpoint` 关联的状态。参见[短期内存](#short-term-memory)。 |
| **store**    | [BaseStore][langgraph.store.base.BaseStore] 的实例。对[长期内存](/oss/langgraph/use-functional-api#long-term-memory)很有用。 |
| **writer**   | 当处理异步 Python < 3.11 时，用于访问 StreamWriter。参见[使用函数式 API 进行流式传输](/oss/langgraph/use-functional-api#streaming)以获取详细信息。 |
| **config**   | 用于访问运行时配置。有关信息，请参阅[RunnableConfig](https://python.langchain.com/docs/concepts/runnables/#runnableconfig)。 |

<Warning>
使用适当的名称和类型注解声明参数。
</Warning>

<Accordion title="请求可注入参数">
  ```python
  from langchain_core.runnables import RunnableConfig
  from langgraph.func import entrypoint
  from langgraph.store.base import BaseStore
  from langgraph.store.memory import InMemoryStore

  in_memory_store = InMemoryStore(...)  # 用于长期内存的 InMemoryStore 实例

  @entrypoint(
      checkpointer=checkpointer,  # 指定检查点
      store=in_memory_store  # 指定存储
  )
  def my_workflow(
      some_input: dict,  # 输入（例如，通过 `invoke` 传递）
      *,
      previous: Any = None, # 用于短期内存
      store: BaseStore,  # 用于长期内存
      writer: StreamWriter,  # 用于流式传输自定义数据
      config: RunnableConfig  # 用于访问传递给入口点的配置
  ) -> ...:
  ```
</Accordion>
:::

### 执行

:::python

<Tabs>
    <Tab title="调用 (Invoke)">
    ```python

        "configurable": {
            "thread_id": "some_thread_id"

    ```
    </Tab>
    <Tab title="异步调用 (Async Invoke)">
    ```python
    config = {
        "configurable": {
            "thread_id": "some_thread_id"
        }
    }
    await my_workflow.ainvoke(some_input, config)  # 异步等待结果
    ```
    </Tab>
    <Tab title="流式传输 (Stream)">
    ```python
    config = {
        "configurable": {
            "thread_id": "some_thread_id"
        }
    }

    for chunk in my_workflow.stream(some_input, config):
        print(chunk)
    ```
    </Tab>
    <Tab title="异步流式传输 (Async Stream)">
    ```python
    config = {
        "configurable": {
            "thread_id": "some_thread_id"
        }
    }

    async for chunk in my_workflow.astream(some_input, config):
        print(chunk)
    ```
    </Tab>
</Tabs>
:::

### 短期内存 (Short-term memory)

当使用 `checkpointer` 定义 `entrypoint` 时，它会在同一**线程 ID** 的连续调用之间将信息存储在[检查点 (checkpoints)](/oss/langgraph/persistence#checkpoints) 中。

:::python
这使得可以使用 `previous` 参数来访问前一次调用的状态[^2]。

默认情况下，`previous` 参数是前一次调用的返回值。

```python
@entrypoint(checkpointer=checkpointer)
def my_workflow(number: int, *, previous: Any = None) -> int:
    previous = previous or 0
    return number + previous

config = {
    "configurable": {
        "thread_id": "some_thread_id"
    }
}

my_workflow.invoke(1, config)  # 1 (previous 是 None)
my_workflow.invoke(2, config)  # 3 (previous 是前一次调用的 1)
```
:::

:::js
这使得可以使用 `getPreviousState` 函数来访问前一次调用的状态。

默认情况下，`getPreviousState` 函数返回前一次调用的返回值。

```typescript
import { entrypoint, getPreviousState } from "@langchain/langgraph";

const myWorkflow = entrypoint(
  { checkpointer, name: "workflow" },
  async (number: number) => {
    const previous = getPreviousState<number>() ?? 0;
    return number + previous;
  }
);

const config = {
  configurable: {
    thread_id: "some_thread_id",
  },
};

await myWorkflow.invoke(1, config); // 1 (previous 是 undefined)
await myWorkflow.invoke(2, config); // 3 (previous 是前一次调用的 1)
```
:::

#### `entrypoint.final`

:::python
@[`entrypoint.final`][entrypoint.final] 是一个特殊的原语，可以从入口点返回，它允许**解耦****保存在检查点**中的值与**入口点**的返回值。

第一个值是入口点的返回值，第二个值是将在检查点中保存的值。类型注解是 `entrypoint.final[return_type, save_type]`。

```python
@entrypoint(checkpointer=checkpointer)
def my_workflow(number: int, *, previous: Any = None) -> entrypoint.final[int, int]:
    previous = previous or 0
    # 这将把前一个值返回给调用者，同时将
    # 2 * number 保存到检查点，供下一个调用用作
    # `previous` 参数。
    return entrypoint.final(value=previous, save=2 * number)

config = {
    "configurable": {
        "thread_id": "1"
    }
}

my_workflow.invoke(3, config)  # 0 (previous 是 None)
my_workflow.invoke(1, config)  # 6 (previous 是前一次调用的 3 * 2)
```
:::

:::js
@[`entrypoint.final`][entrypoint.final] 是一个特殊的原语，可以从入口点返回，它允许**解耦****保存在检查点**中的值与**入口点**的返回值。

第一个值是入口点的返回值，第二个值是将在检查点中保存的值。

```typescript
import { entrypoint, getPreviousState } from "@langchain/langgraph";

```

## 任务 (Task)

**任务 (Task)** 代表一个离散的工作单元，例如 API 调用或数据处理步骤。它有两个关键特性：

* **异步执行 (Asynchronous Execution)**: 任务设计为异步执行，允许多个操作并发运行而不会阻塞。
* **检查点 (Checkpointing)**: 任务结果会保存到检查点中，从而可以在工作流从上次保存的状态恢复。 (有关更多详细信息，请参阅[持久化](/oss/langgraph/persistence))。

### 定义

:::python
使用 `@task` 装饰器定义任务，该装饰器包装一个常规的 Python 函数。

```python
from langgraph.func import task

@task()
def slow_computation(input_value):
    # 模拟长时间运行的操作
    ...
    return result
```
:::

:::js
使用 `task` 函数定义任务，该函数包装一个常规函数。

```typescript
import { task } from "@langchain/langgraph";

const slowComputation = task("slowComputation", async (inputValue: any) => {
  // 模拟长时间运行的操作
  return result;
});
```
:::

<Warning>
**序列化 (Serialization)**
任务的**输出**必须是 JSON 可序列化的，以支持检查点功能。
</Warning>

### 执行

**任务**只能在**入口点**、另一个**任务**或[状态图节点](/oss/langgraph/graph-api#nodes)内部被调用。

任务_不能_直接从主应用程序代码中调用。

:::python
当您调用一个**任务**时，它会立即返回一个 future 对象。Future 是一个占位符，表示稍后才能获得的结果。

要获取**任务**的结果，您可以同步等待它（使用 `result()`），或者异步等待它（使用 `await`）。

<Tabs>
    <Tab title="同步调用 (Synchronous Invocation)">
    ```python
    @entrypoint(checkpointer=checkpointer)
    def my_workflow(some_input: int) -> int:
        future = slow_computation(some_input)
        return future.result()  # 同步等待结果
    ```
    </Tab>
    <Tab title="异步调用 (Asynchronous Invocation)">
    ```python
    @entrypoint(checkpointer=checkpointer)
    async def my_workflow(some_input: int) -> int:
        return await slow_computation(some_input)  # 异步等待结果
    ```
    </Tab>
</Tabs>
:::

:::js
当您调用一个**任务**时，它会返回一个可以等待的 Promise。

```typescript
const myWorkflow = entrypoint(
  { checkpointer, name: "workflow" },
  async (someInput: number): Promise<number> => {
    return await slowComputation(someInput);
  }
);
```
:::

## 何时使用任务 (When to use a task)

在以下场景中，**任务**非常有用：

* **检查点 (Checkpointing)**: 当您需要将长时间运行操作的结果保存到检查点时，这样在恢复工作流时就不必重新计算它。
* **人工干预 (Human-in-the-loop)**: 如果您正在构建需要人工干预的工作流，则**必须**使用**任务**来封装任何随机性（例如 API 调用），以确保工作流可以正确恢复。有关更多详细信息，请参阅[确定性](#determinism)部分。
* **并行执行**: 对于 I/O 密集型任务，**任务**支持并行执行，允许多个操作并发运行而不阻塞（例如，调用多个 API）。
* **可观测性 (Observability)**: 将操作包装在**任务**中提供了一种跟踪工作流进度并使用 [LangSmith](https://docs.langchain.com/langsmith/home) 监控单个操作执行的方式。
* **可重试工作 (Retryable Work)**: 当工作需要重试以处理失败或不一致性时，**任务**提供了一种封装和管理重试逻辑的方式。

## 序列化 (Serialization)

LangGraph 序列化有两个关键方面：

1. `entrypoint` 的输入和输出必须是 JSON 可序列化的。
2. `task` 的输出必须是 JSON 可序列化的。

:::python
这些要求对于启用检查点和工作流恢复是必需的。请使用 Python 原语，如字典、列表、字符串、数字和布尔值，以确保您的输入和输出是可序列化的。
:::

:::js
这些要求对于启用检查点和工作流恢复是必需的。请使用对象、数组、字符串、数字和布尔值等原语，以确保您的输入和输出是可序列化的。
:::

序列化确保工作流状态（如任务结果和中间值）可以可靠地保存和恢复。这对于启用人工干预交互、容错和并行执行至关重要。

提供不可序列化的输入或输出，在配置了检查点的

工作流运行时将导致运行时错误。

## 确定性 (Determinism)

为了利用**人工干预**等特性，任何随机性都应该封装在**任务**内部。这确保了当执行暂停（例如，为了人工干预）然后恢复时，它将遵循相同的_步骤序列_，即使**任务**结果是**非确定性**的也是如此。

LangGraph 通过在执行过程中持久化**任务**和[**子图**](/oss/langgraph/use-subgraphs)结果来实现这种行为。设计良好的工作流可确保恢复执行遵循_相同的步骤序列_，从而允许正确检索中断前执行的先前计算结果，而无需重新执行它们。这对于长时间运行的**任务**或具有非确定性结果的**任务**特别有用，因为它避免了重复已完成的工作，并允许从本质上相同的点恢复执行。

虽然工作流的不同运行可以产生不同的结果，但恢复**特定**运行应始终遵循相同的记录步骤序列。这允许 LangGraph 高效地查找先前已执行的**任务**和**子图**结果，并避免重新计算它们。

## 幂等性 (Idempotency)

幂等性确保多次运行相同的操作会产生相同的结果。这有助于防止由于步骤重试而导致的重复 API 调用和冗余处理。始终将 API 调用放在 **任务** 函数中以进行检查点设置，并设计它们在重新执行时具有幂等性。如果一个**任务**开始但未能成功完成，可能会发生重新执行。然后，如果在恢复工作流时，该**任务**将再次运行。使用幂等性键或验证现有结果以避免重复。

## 常见陷阱 (Common Pitfalls)

### 处理副作用 (Handling side effects)

将副作用（例如写入文件、发送电子邮件）封装在任务中，以确保它们在恢复工作流时不会被多次执行。

<Tabs>
    <Tab title="错误 (Incorrect)">
    在此示例中，副作用（写入文件）直接包含在工作流中，因此在恢复工作流时它将被执行第二次。

    :::python
    ```python
    @entrypoint(checkpointer=checkpointer)
    def my_workflow(inputs: dict) -> int:
        # 当恢复工作流时，此代码将第二次执行。
        # 这很可能不是您想要的。
        with open("output.txt", "w") as f:  # [!code highlight]
            f.write("Side effect executed")  # [!code highlight]
        value = interrupt("question")
        return value
```
    :::

    :::js
    ```typescript
    import { entrypoint, interrupt } from "@langchain/langgraph";
    import fs from "fs";

    const myWorkflow = entrypoint(
      { checkpointer, name: "workflow" },
      async (inputs: Record<string, any>) => {

        fs.writeFileSync("output.txt", "Side effect executed");

        return value;
      }
    ```

    </Tab>
    <Tab title="正确 (Correct)">
    在此示例中，副作用被封装在一个任务中，确保恢复执行时的一致性。

    ```python
        # 副作用现在封装在一个任务中。
        write_to_file().result()
        value = interrupt("question")
        return value
```
    :::

    :::js

### 非确定性控制流 (Non-deterministic control flow)

每次可能产生不同结果的操作（如获取当前时间或随机数）应封装在任务中，以确保恢复时返回相同的结果。

* 在任务中：获取随机数 (5) → 中断 → 恢复 → (再次返回 5) → ...
* 不在任务中：获取随机数 (5) → 中断 → 恢复 → 获取新的随机数 (7) → ...

:::python
当使用具有多个中断调用的**人工干预**工作流时，这一点尤为重要。LangGraph 会为每个任务/入口点保留一个恢复值列表。遇到中断时，它会与相应的恢复值匹配。这种匹配是严格**基于索引**的，因此恢复值的顺序应与中断的顺序相匹配。
:::

:::js
当使用具有多个中断调用的**人工干预**工作流时，这一点尤为重要。LangGraph 会为每个任务/入口点保留一个恢复值列表。遇到中断时，它会与相应的恢复值匹配。这种匹配是严格**基于索引**的，因此恢复值的顺序应与中断的顺序相匹配。
:::

如果在恢复执行时未保持执行顺序，一个 @[`interrupt`] 调用可能会与错误的 `resume` 值匹配，从而导致错误的结果。

请阅读[确定性](#determinism)部分以获取更多详细信息。
