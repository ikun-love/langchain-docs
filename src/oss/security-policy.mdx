LangChain 拥有一个庞大的生态系统，集成了各种外部资源，例如本地和远程文件系统、API 和数据库。这些集成允许开发者创建多功能应用程序，将大型语言模型（LLM）的能力与访问、交互和操作外部资源的能力相结合。

## 最佳实践

在构建此类应用程序时，开发者应记住遵循良好的安全实践：

* [**限制权限**](https://en.wikipedia.org/wiki/Principle_of_least_privilege)（最小权限原则）：将权限范围限定在应用程序的实际需求之内。授予宽泛或过多的权限可能会引入重大的安全漏洞。为避免此类漏洞，请根据应用程序的需要，考虑使用只读凭证、禁止访问敏感资源、使用沙箱技术（例如在容器内运行）、指定代理配置来控制外部请求等方法。
* **预见潜在的滥用**：正如人类会犯错一样，大型语言模型（LLM）也可能出错。请始终假设任何系统访问或凭证都可能以其被分配的权限所允许的任何方式被使用。例如，如果一组数据库凭证允许删除数据，那么最安全假设是任何能够使用这些凭证的 LLM 都可能确实会删除数据。
* [**深度防御**](https://en.wikipedia.org/wiki/Defense_in_depth_(computing))（纵深防御）：没有哪一种安全技术是完美的。精细调整 (Fine-tuning) 和良好的链式设计可以减少 LLM 犯错的几率，但不能消除它。最好是结合多种分层安全方法，而不是依赖任何单一的防御层来确保安全。例如：同时使用只读权限和沙箱技术，以确保 LLM 只访问明确允许它们使用的​​数据。

如果不遵循这些实践，可能带来的风险包括但不限于：

* 数据损坏或丢失。
* 未经授权访问机密信息。
* 关键资源性能或可用性受到侵害。

带有缓解策略的示例场景：

* 用户可能会要求一个有权访问文件系统的代理删除不应该删除的文件，或者读取包含敏感信息的文件内容。为缓解此问题，请将该代理的权限限制为仅使用特定目录，并仅允许它读取或写入安全的文件。可以考虑通过在容器中运行代理来进一步对代理进行沙箱化。
* 用户可能会要求一个有权写入外部 API 的代理向 API 写入恶意数据，或从该 API 中删除数据。为缓解此问题，请为代理提供只读 API 密钥，或将其限制为仅使用那些在设计上已经能抵抗此类滥用的端点。
* 用户可能会要求一个有权访问数据库的代理执行 `drop table`（删除表）操作或修改数据库架构。为缓解此问题，请将凭证的范围限定为代理仅需要访问的表，并考虑发放只读凭证。

如果您正在构建需要访问文件系统、API 或数据库等外部资源的应用程序，请考虑咨询公司的安全团队，以确定如何最好地设计和保护您的应用程序。

## 报告开源软件漏洞

请使用以下流程报告与 LangChain 开源项目相关的安全漏洞：

1. **在存在漏洞的 GitHub 仓库**的 “Security”（安全）选项卡中**提交安全建议 (security advisory)**。
2. **发送电子邮件**到 `security@langchain.dev` 通知我们您已提交安全问题以及该问题存在于哪个仓库中。

在报告漏洞之前，请查看上面的[最佳实践](#best-practices)，以了解我们认为哪些情况属于安全漏洞，哪些属于开发人员的责任范围。

### Bug 赏金资格

我们欢迎针对所有 LangChain 库的安全漏洞报告。但是，我们可能仅对以下软件包中的漏洞提供临时性 Bug 赏金：

* LangChain 团队拥有和维护的核心库：`langchain-core`、`langchain` (v1)、`langgraph` 以及相关的检查点 (checkpointer) 包（或其 JavaScript 等效项）
* LangChain 团队维护的热门集成（例如 `langchain-openai`、`langchain-anthropic` 等，或其 JavaScript 等效项）

漏洞必须存在于库代码本身，而不是示例代码或示例应用程序中。

我们欢迎对所有其他 LangChain 包的报告，并将解决有效的安全问题，但对于超出此范围的软件包将不授予 Bug 赏金。这包括 `langchain-community`，由于其社区驱动的性质，它不符合 Bug 赏金的条件，但我们仍将接受并处理相关报告。

### 范围外的目标

以下情况不属于安全漏洞报告的范围：

* **langchain-experimental**：此仓库用于实验性代码，不在安全报告的范围内（参见 [package warning](https://pypi.org/project/langchain-experimental/)）。
* **示例和示例应用程序**：示例代码和演示应用程序不在安全报告的范围内。
* **已记录安全声明的代码**：这将根据具体情况决定，但很可能不在范围内，因为代码已经记录了开发人员应遵循的指南以确保应用程序安全。
* **LangSmith 相关的仓库或 API**：请参阅下文中的[报告 LangSmith 漏洞](#reporting-langsmith-vulnerabilities)。
