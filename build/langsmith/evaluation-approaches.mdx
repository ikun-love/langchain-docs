下面，我们将讨论对几种流行的 LLM 应用类型的评估方法。

## 智能体 (Agents)

[LLM 驱动的自主智能体](https://lilianweng.github.io/posts/2023-06-23-agent/) 结合了三个组件：(1) 工具调用 (Tool calling)、(2) 记忆 (Memory) 和 (3) 规划 (Planning)。智能体利用工具调用（例如，通常通过提示工程实现）和记忆（例如，通常是短期消息历史记录）来生成响应。[工具调用](https://python.langchain.com/v0.1/docs/modules/model_io/chat/function_calling/) 允许模型通过生成两项内容来响应给定的提示：(1) 要调用的工具 和 (2) 所需的输入参数。

![Tool use](/langsmith/images/tool-use.png)

下面是一个使用 [LangGraph](https://langchain-ai.github.io/langgraph/tutorials/introduction/) 实现的工具调用智能体示例。`assistant node`（助手节点）是一个 LLM，它根据输入决定是否调用工具。`tool condition`（工具条件）检查 `assistant node` 是否选择了工具，如果选中，则路由到 `tool node`（工具节点）。`tool node` 执行工具，并将输出作为工具消息返回给 `assistant node`。这个循环会持续进行，只要 `assistant node` 持续选择工具。如果没有选择工具，智能体将直接返回 LLM 的响应。

![Agent](/langsmith/images/langgraph-agent.png)

这确定了用户通常感兴趣的三种通用智能体评估类型：

* `Final Response`（最终响应）：评估智能体的最终响应。
* `Single step`（单步）：隔离评估智能体的任意一步（例如，它是否选择了正确的工具）。
* `Trajectory`（轨迹）：评估智能体是否遵循了预期的路径（例如，预期的工具调用序列）来得出最终答案。

![Agent-eval](/langsmith/images/agent-eval.png)

下面我们将介绍这些评估方法的具体内容，需要的组件（输入、输出、评估器），以及何时应考虑使用它们。请注意，您很可能希望进行多种（如果不是全部！）这些类型的评估——它们并非相互排斥！

### 评估智能体的最终响应

评估智能体的一种方法是评估其在任务上的总体性能。这基本上是将智能体视为一个黑盒，只评估它是否完成了工作。

输入应该包括用户输入和（可选的）工具列表。在某些情况下，工具是作为智能体的一部分硬编码的，无需传入。在其他情况下，智能体更通用，意味着它没有固定的工具集，需要在运行时传入工具。

输出应该是智能体的最终响应。

评估器取决于您要求智能体执行的任务。许多智能体执行一系列相对复杂的操作，并输出最终的文本响应。与 RAG 类似，LLM-作为-裁判 (LLM-as-judge) 评估器在这种情况下通常很有效，因为它们可以直接从文本响应中评估智能体是否完成了工作。

然而，此类评估有几个缺点。首先，运行通常需要较长时间。其次，您没有评估智能体内部发生的事情，因此在发生故障时很难进行调试。第三，有时很难定义合适的评估指标。

### 评估智能体的单步操作

智能体通常执行多个操作。虽然端到端地评估它们很有用，但单独评估这些操作也很有用。这通常涉及到评估智能体的单个步骤——即 LLM 决定下一步做什么的调用。

输入应该是单个步骤的输入。根据您测试的内容，这可能仅仅是原始用户输入（例如，提示和/或一组工具），也可能包括先前已完成的步骤。

输出仅仅是该步骤的输出，通常是 LLM 的响应。LLM 响应通常包含工具调用，指示智能体接下来应采取什么操作。

这种情况下的评估器通常是关于是否选择了正确的工具调用的某种二元分数，以及关于工具输入是否正确的某种启发式方法。参考工具可以简单地指定为一个字符串。

此类评估有几个好处。它允许您评估单个操作，从而帮助您精确定位应用程序可能出现故障的位置。它们运行速度也相对较快（因为它们只涉及一次 LLM 调用），并且评估通常使用选定的工具相对于参考工具的简单启发式评估。一个缺点是它们没有捕获完整的智能体——只捕获了特定的一步。另一个缺点是数据集创建可能很具有挑战性，特别是当您希望在智能体输入中包含过去的历史记录时。生成智能体轨迹早期步骤的数据集是相当容易的（例如，可能只包括输入提示），但为轨迹中后期的步骤生成数据集可能会很困难（例如，包括众多的先前智能体操作和响应）。

### 评估智能体的轨迹

评估智能体的轨迹涉及评估智能体采取的所有步骤。

输入再次是整个智能体的输入（用户输入，以及可选的工具列表）。

输出是工具调用的列表，可以被构建为“精确”轨迹（例如，预期的工具调用序列）或仅仅是一组预期的工具调用（按任意顺序排列）。

此处的评估器是作用于所采取步骤的某个函数。评估“精确”轨迹可以使用单一的二元分数来确认序列中每个工具名称的精确匹配。这很简单，但存在一些缺陷。有时可能有多个正确的路径。此评估也不能反映轨迹偏离一个步骤或完全错误之间的区别。

为了解决这些缺陷，评估指标可以侧重于采取的“不正确”步骤的数量，这能更好地衡量接近的轨迹和严重偏离的轨迹之间的差异。评估指标也可以侧重于是否按任意顺序调用了所有预期的工具。

然而，所有这些方法都没有评估工具的输入；它们只关注所选择的工具。为了解决这个问题，另一种评估技术是将完整的智能体轨迹（连同参考轨迹）作为一组消息（例如，所有 LLM 响应和工具调用）传递给 LLM-作为-裁判。这可以评估智能体的完整行为，但是编译参考轨迹是最具挑战性的（幸运的是，使用 LangGraph 等框架可以提供帮助！）。另一个缺点是评估指标可能有点棘手。

## 检索增强生成 (RAG)

检索增强生成 (RAG) 是一种强大的技术，涉及根据用户的输入检索相关文档，并将它们传递给语言模型进行处理。RAG 通过利用外部知识库，使 AI 应用程序能够生成更具信息量和上下文感知的响应。

<Info>
有关 RAG 概念的全面回顾，请参阅我们的 [`RAG 从零开始` 系列](https://github.com/langchain-ai/rag-from-scratch)。
</Info>

### 数据集

在评估 RAG 应用时，一个关键的考虑因素是您是否拥有（或能否轻松获取）每个输入问题的参考答案。参考答案作为评估生成响应正确性的真实标准（Ground Truth）。然而，即使没有参考答案，仍然可以使用参考无关的 RAG 评估提示（下面提供了示例）来执行各种评估。

### 评估器

`LLM-作为-裁判` 是 RAG 中常用的评估器，因为它是一种评估事实准确性或文本之间一致性的有效方法。

![rag-types.png](/langsmith/images/rag-types.png)

在评估 RAG 应用时，您可以拥有需要参考输出的评估器，也可以拥有不需要参考输出的评估器：

1. **需要参考输出**：将 RAG 链生成的答案或检索到的内容与参考答案（或检索结果）进行比较，以评估其正确性。
2. **不需要参考输出**：使用不需要参考答案的提示（在上图中由橙色、绿色和红色表示）执行自我一致性检查。

### 应用 RAG 评估

在应用 RAG 评估时，请考虑以下方法：

1. `Offline evaluation`（离线评估）：对任何依赖参考答案的提示使用离线评估。这最常用于 RAG 答案正确性评估，其中参考是真实（正确）的答案。

2. `Online evaluation`（在线评估）：对任何参考无关的提示使用在线评估。这允许您在实时场景中评估 RAG 应用的性能。

3. `Pairwise evaluation`（成对评估）：利用成对评估来比较由不同 RAG 链生成的答案。此类评估侧重于用户指定的标准（例如，答案格式或风格），而不是正确性（正确性可以使用自我一致性或真实参考来评估）。

### RAG 评估总结

| 评估器 | 详情 | 需要参考输出 | LLM-作为-裁判? | 成对相关 |
| :--- | :--- | :--- | :--- | :--- |
| Document relevance（文档相关性） | 文档与问题相关吗？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/rag-document-relevance) | 否 |
| Answer faithfulness（答案忠实度） | 答案是否基于文档内容？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/rag-answer-hallucination) | 否 |
| Answer helpfulness（答案帮助性） | 答案是否有助于解决问题？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/rag-answer-helpfulness) | 否 |
| Answer correctness（答案正确性） | 答案是否与参考答案一致？ | 是 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/rag-answer-vs-reference) | 否 |
| Pairwise comparison（成对比较） | 多个答案版本如何比较？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/pairwise-evaluation-rag) | 是 |

## 摘要 (Summarization)

摘要是自由格式写作的一种特定类型。评估目标通常是根据一组标准来检验这段文字（摘要）的表现。

通常使用开发人员策划的文本示例（Developer curated examples）来进行摘要评估（[此处](https://smith.langchain.com/public/659b07af-1cab-4e18-b21a-91a69a4c3990/d) 可查看数据集示例）。然而，生产中（摘要）应用的**用户日志**可以用于在线评估，过程采用下面任意一种**参考无关**的评估提示。

`LLM-作为-裁判` 通常用于摘要（以及其他类型的写作）的评估，方法是使用遵循所提供标准的**参考无关**提示来对摘要进行评分。提供特定的**参考**摘要的情况较少，因为摘要是一项创造性任务，存在许多可能的正确答案。

由于使用了**参考无关**提示，**在线**或**离线**评估都是可行的。**成对**评估也是比较不同摘要链（例如，不同的摘要提示或 LLM）的有力方式：

| 用例 | 详情 | 需要参考输出 | LLM-作为-裁判? | 成对相关 |
| :--- | :--- | :--- | :--- | :--- |
| Factual accuracy（事实准确性） | 摘要相对于源文档是否准确？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/summary-accurancy-evaluator) | 是 |
| Faithfulness（忠实度） | 摘要是否基于源文档（例如，没有幻觉）？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/summary-hallucination-evaluator) | 是 |
| Helpfulness（帮助性） | 摘要是否满足用户需求？ | 否 | 是 - [提示](https://smith.langchain.com/hub/langchain-ai/summary-helpfulness-evaluator) | 是 |

## 分类和标记 (Classification and tagging)

分类和标记是对给定输入应用标签（例如，用于毒性检测、情感分析等）。分类/标记评估通常采用以下组件，我们将在下面进行详细回顾：

分类/标记评估的一个核心考虑因素是您是否有一个包含**参考**标签的数据集。如果没有，用户通常希望定义一个评估器，该评估器使用标准来对输入（例如，文本、用户问题等）应用标签（例如，毒性等）。但是，如果提供了真实类标签（ground truth class labels），那么评估目标就侧重于根据真实类标签对分类/标记链进行评分（例如，使用精确率、召回率等指标）。

如果提供了真实参考标签，则通常只需定义一个[自定义启发式评估器](/langsmith/code-evaluator)来比较真实标签和链的输出。然而，随着 LLM 的出现，越来越多地使用 `LLM-作为-裁判` 来根据指定的标准（无需真实参考）执行输入的分类/标记。

使用带有**参考无关**提示的 `LLM-作为-裁判`，可以实现**在线**或**离线**评估。这特别适合**在线**评估，当用户想要标记/分类应用输入（例如，用于毒性等）时。

| 用例 | 详情 | 需要参考输出 | LLM-作为-裁判? | 成对相关 |
| :--- | :--- | :--- | :--- | :--- |
| Accuracy（准确率） | 标准定义 | 是 | 否 | 否 |
| Precision（精确率） | 标准定义 | 是 | 否 | 否 |
| Recall（召回率） | 标准定义 | 是 | 否 | 否 |
