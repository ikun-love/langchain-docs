---
title: 持久化 (Persistence)
---

LangGraph 内置了一个持久化层，通过 **Checkpointer（检查点保存器）** 来实现。当你使用带有 Checkpointer 编译图（Graph）时，Checkpointer 会在每一步超步（super-step）保存图状态的 `checkpoint`。这些检查点被保存在一个称为 `thread`（线程）中，该线程在图执行后可以被访问。由于 `thread` 允许在执行后访问图的状态，因此得以实现：人机协作（human-in-the-loop）、内存（memory）、时间旅行（time travel）和容错（fault-tolerance）等强大功能。下面我们将详细讨论每个概念。

![Checkpoints](/oss/images/checkpoints.jpg)

<Info>
**LangGraph API 自动处理检查点**
在使用 LangGraph API 时，您无需手动实现或配置 Checkpointer。API 会在后台为您处理所有的持久化基础设施。
</Info>

## 线程 (Threads)

`Thread` 是一个唯一的 ID 或线程标识符，分配给 Checkpointer 保存的每个检查点。它包含了一系列 [运行 (runs)](/langsmith/assistants#execution) 的累积状态。当一个运行被执行时，助手底层图的状态 (the state of the underlying graph of the assistant) 将被持久化到该线程中。

当使用 Checkpointer 调用图时，您 **必须** 在 `config` 的 `configurable` 部分指定一个 `thread_id`：



```typescript
{
  configurable: {
    thread_id: "1";
  }
}
```


可以检索线程的当前状态和历史状态。为了持久化状态，必须在执行运行之前创建该线程。LangSmith API 提供了几个用于创建和管理线程及线程状态的端点。有关更多详细信息，请参阅 [API 参考](https://reference.langchain.com/python/langsmith/)。

Checkpointer 使用 `thread_id` 作为存储和检索检查点的**主键**。如果没有它，Checkpointer 将无法保存状态或在 [中断 (interrupt)](/oss/javascript/langgraph/interrupts) 后恢复执行，因为它需要 `thread_id` 来加载保存的状态。

## 检查点 (Checkpoints)

在特定时间点上一个线程的状态被称为一个检查点（Checkpoint）。检查点是保存于每个超步的图状态的快照，由具有以下关键属性的 `StateSnapshot` 对象表示：

* `config`: 与此检查点关联的配置。
* `metadata`: 与此检查点关联的元数据。
* `values`: 此时间点的状态通道的值。
* `next`: 一个元组，包含图中最先要执行的节点名称。
* `tasks`: 一个包含有关接下来要执行的任务信息的 `PregelTask` 对象元组。如果该步骤之前已被尝试过，它将包含错误信息。如果图在节点内部被 [动态地](/oss/javascript/langgraph/interrupts#pause-using-interrupt) 中断，`tasks` 将包含与中断相关的附加数据。

检查点被持久化，并可用于在以后恢复线程的状态。

让我们看看当以下面的方式调用一个简单图时保存了哪些检查点：



```typescript
import { StateGraph, START, END, MemoryServer } from "@langchain/langgraph";
import { registry } from "@langchain/langgraph/zod";
import * as z from "zod";

const State = z.object({
  foo: z.string(),
  bar: z.array(z.string()).register(registry, {
    reducer: {
      fn: (x, y) => x.concat(y),
    },
    default: () => [] as string[],
  }),
});

const workflow = new StateGraph(State)
  .addNode("nodeA", (state) => {
    return { foo: "a", bar: ["a"] };
  })
  .addNode("nodeB", (state) => {
    return { foo: "b", bar: ["b"] };
  })
  .addEdge(START, "nodeA")
  .addEdge("nodeA", "nodeB")
  .addEdge("nodeB", END);

const checkpointer = new MemorySaver();
const graph = workflow.compile({ checkpointer });

const config = { configurable: { thread_id: "1" } };
await graph.invoke({ foo: "", bar: [] }, config);
```

执行图后，我们期望看到正好 4 个检查点：

* 初始检查点，下一个要执行的节点为 [`START`](https://reference.langchain.com/javascript/variables/_langchain_langgraph.index.START.html)
* 带有用户输入 `{'foo': '', 'bar': []}` 的检查点，下一个要执行的节点为 `nodeA`
* 带有 `nodeA` 输出 `{'foo': 'a', 'bar': ['a']}` 的检查点，下一个要执行的节点为 `nodeB`
* 带有 `nodeB` 输出 `{'foo': 'b', 'bar': ['a', 'b']}` 的检查点，没有下一个要执行的节点

请注意，由于 `bar` 通道定义了累加器（reducer），其值包含了来自两个节点的输出。


### 获取状态 (Get state)



在与已保存的图状态交互时，您 **必须** 指定一个 [线程标识符](#threads)。您可以通过调用 `graph.getState(config)` 来查看图的**最新**状态。这将返回一个 `StateSnapshot` 对象，它对应于配置中提供的线程 ID 的最新检查点，或者对应于该线程中特定检查点 ID 的检查点（如果提供了 `checkpoint_id`）。

```typescript
// 获取最新的状态快照
const config = { configurable: { thread_id: "1" } };
await graph.getState(config);

// 获取特定 checkpoint_id 的状态快照
const config = {
  configurable: {
    thread_id: "1",
    checkpoint_id: "1ef663ba-28fe-6528-8002-5a559208592c",
  },
};
await graph.getState(config);
```

### 重放 (Replay)

也可以重放（play-back）先前的图执行。如果我们用一个 `thread_id` 和一个 `checkpoint_id` 调用图，那么我们将**重放**在对应于 `checkpoint_id` 的检查点之前已经执行过的步骤，并且只执行该检查点之后的步骤。

* `thread_id` 是一个线程的 ID。
* `checkpoint_id` 是一个标识符，指向线程内的一个特定检查点。

您必须在调用图时将这些信息作为 `config` 的 `configurable` 部分传入：



```typescript
const config = {
  configurable: {
    thread_id: "1",
    checkpoint_id: "0c62ca34-ac19-445d-bbb0-5b4984975b2a",
  },
};
await graph.invoke(null, config);
```


重要的是，LangGraph 知道特定步骤是否已被执行过。如果已经执行过，LangGraph 只会_重放_该特定步骤，而不会重新执行它，但这仅针对 `checkpoint_id` 之前的步骤。`checkpoint_id` 之后的所有步骤都将被执行（即，一个新的分支），即使它们之前已被执行过。请参阅这篇关于时间旅行的 [操作指南](/oss/javascript/langgraph/use-time-travel) 以了解有关重放的更多信息。

### 更新状态 (Update state)



除了从特定的 `checkpoints` 中重放图之外，我们还可以_编辑_图状态。我们使用 `graph.updateState()` 来实现这一点。此方法接受三个不同的参数：


#### `config`

`config` 应包含 `thread_id` 以指定要更新哪个线程。仅当传入 `thread_id` 时，我们更新（或分支）当前状态。如果包含 `checkpoint_id` 字段，则可以从选定的检查点进行分支。

#### `values`

这些是用于更新状态的值。请注意，此更新的处理方式与来自节点的任何更新完全相同。这意味着这些值将被传递给 [累加器 (reducer)](/oss/javascript/langgraph/graph-api#reducers) 函数（如果它们是图状态中某些通道的定义）。这意味着 [`update_state`](https://reference.langchain.com/javascript/classes/_langchain_langgraph.pregel.Pregel.html#updateState) **不会**自动覆盖所有通道的值，而只覆盖没有累加器的通道。让我们通过一个例子来了解。

假设您已使用以下架构定义了图的状态（参见上面的完整示例）：



```typescript
import { registry } from "@langchain/langgraph/zod";
import * as z from "zod";

const State = z.object({
  foo: z.number(),
  bar: z.array(z.string()).register(registry, {
    reducer: {
      fn: (x, y) => x.concat(y),
    },
    default: () => [] as string[],
  }),
});
```


现在假设图的当前状态是



```typescript
{ foo: 1, bar: ["a"] }
```


如果您如下所示更新状态：



```typescript
await graph.updateState(config, { foo: 2, bar: ["b"] });
```


那么图的新状态将是：



```typescript
{ foo: 2, bar: ["a", "b"] }
```

`foo` 键（通道）被完全更改（因为没有为该通道指定累加器，所以 `updateState` 会直接覆盖它）。但是，为 `bar` 键指定了累加器，因此它会将 `"b"` 追加到 `bar` 的状态中。


#### `as_node`



调用 `updateState` 时可以可选地指定的最后一项是 `asNode`。如果您提供了它，则更新将被应用，就好像它来自名为 `asNode` 的节点一样。如果未提供 `asNode`，它将在不模糊的情况下设置为最后更新状态的节点。这很重要，因为下一步骤的执行取决于最后一个提供更新的节点，因此可用于控制哪个节点下一步执行。请参阅这篇关于时间旅行的 [操作指南](/oss/javascript/langgraph/use-time-travel) 了解有关分支状态的更多信息。

## 内存存储 (Memory Store)

![Model of shared state](/oss/images/shared_state.png)

[状态架构 (State schema)](/oss/javascript/langgraph/graph-api#schema) 定义了一组在图执行过程中被填充的键。如上所述，状态可以在每个图步骤被 checkpointer 写入线程，从而实现状态持久化。

但是，如果我们想在**线程之间**保留某些信息该怎么办？考虑一个聊天机器人场景，我们希望保留关于用户的特定信息，跨越与该用户的所有聊天会话（即所有线程）！

仅使用 Checkpointer，我们无法在线程之间共享信息。这就引出了对 [`Store`](https://reference.langchain.com/python/langgraph/store/) 接口的需求。作为说明，我们可以定义一个 `InMemoryStore` 来在线程间存储用户信息。我们只需像以前一样，用 checkpointer 编译我们的图，并 ساتھ 我们的新 `in_memory_store` 变量即可。

<Info>
**LangGraph API 自动处理存储 (Store)**
在使用 LangGraph API 时，您无需手动实现或配置 Store。API 会在后台为您处理所有的存储基础设施。
</Info>

### 基本用法 (Basic Usage)

首先，让我们在不使用 LangGraph 的情况下单独展示这一点。



```typescript
import { MemoryStore } from "@langchain/langgraph";

const memoryStore = new MemoryStore();
```


内存是根据一个 `tuple`（元组）进行命名空间化的，在这个特定示例中将是 `(<user_id>, "memories")`。命名空间可以是任意长度并代表任何内容，不一定需要与用户相关。



```typescript
const userId = "1";
const namespaceForMemory = [userId, "memories"];
```


我们使用 `store.put` 方法将内存保存到我们的命名空间中。执行此操作时，我们需要指定命名空间（如上定义），以及内存的键值对：键是内存的唯一标识符（`memory_id`），值（一个字典）是内存本身。



```typescript
import { v4 as uuidv4 } from "uuid";

const memoryId = uuidv4();
const memory = { food_preference: "I like pizza" };
await memoryStore.put(namespaceForMemory, memoryId, memory);
```


我们可以使用 `store.search` 方法读出命名空间中的内存，该方法将返回给定用户的所有内存列表。最新的内存位于列表的末尾。



```typescript
const memories = await memoryStore.search(namespaceForMemory);
memories[memories.length - 1];

// {
//   value: { food_preference: 'I like pizza' },
//   key: '07e0caf4-1631-47b7-b15f-65515d4c1843',
//   namespace: ['1', 'memories'],
//   createdAt: '2024-10-02T17:22:31.590602+00:00',
//   updatedAt: '2024-10-02T17:22:31.590605+00:00'
// }
```

它具有的属性是：

* `value`: 此内存的值
* `key`: 此命名空间中此内存的唯一键
* `namespace`: 字符串列表，此内存类型的命名空间
* `createdAt`: 创建此内存的时间戳
* `updatedAt`: 更新此内存的时间戳


### 语义搜索 (Semantic Search)

除了简单的检索之外，Store 还支持语义搜索，允许您根据含义而非精确匹配来查找内存。要启用此功能，请使用嵌入模型配置 Store：



```typescript
import { OpenAIEmbeddings } from "@langchain/openai";

const store = new InMemoryStore({
  index: {
    embeddings: new OpenAIEmbeddings({ model: "text-embedding-3-small" }),
    dims: 1536,
    fields: ["food_preference", "$"], // 要嵌入的字段
  },
});
```


现在在搜索时，您可以使用自然语言查询来查找相关的内存：



```typescript
// 查找关于饮食偏好的内存
// (在将内存放入存储后可以执行此操作)
const memories = await store.search(namespaceForMemory, {
  query: "What does the user like to eat?",
  limit: 3, // 返回前 3 个匹配项
});
```


您可以通过配置 `fields` 参数或在存储内存时指定 `index` 参数来控制要嵌入内存的哪些部分：



```typescript
// 使用特定字段进行嵌入存储
await store.put(
  namespaceForMemory,
  uuidv4(),
  {
    food_preference: "I love Italian cuisine",
    context: "Discussing dinner plans",
  },
  { index: ["food_preference"] } // 只嵌入 "food_preferences" 字段
);

// 不带嵌入的存储（仍可检索，但不可搜索）
await store.put(
  namespaceForMemory,
  uuidv4(),
  { system_info: "Last updated: 2024-01-01" },
  { index: false }
);
```


### 在 LangGraph 中使用 (Using in LangGraph)



完成所有设置后，我们在 LangGraph 中使用 `memoryStore`。`memoryStore` 与 checkpointer 协同工作：checkpointer 将状态保存到线程（如上所述），而 `memoryStore` 允许我们存储任意信息，以便在**跨**线程访问。我们像下面这样，同时传入 checkpointer 和 `memoryStore` 来编译图。

```typescript
import { MemorySaver } from "@langchain/langgraph";

// 我们需要这个是因为我们想启用线程（会话）
const checkpointer = new MemorySaver();

// ... 定义图 ...

// 用 checkpointer 和 store 编译图
const graph = workflow.compile({ checkpointer, store: memoryStore });
```


我们使用带 `thread_id` 的方式来调用图，就像以前一样，还要带上 `user_id`，我们将用它来为上述的内存设置命名空间。



```typescript
// 调用图
const userId = "1";
const config = { configurable: { thread_id: "1", user_id: userId } };

// 首先我们只和 AI 打个招呼
for await (const update of await graph.stream(
  { messages: [{ role: "user", content: "hi" }] },
  { ...config, streamMode: "updates" }
)) {
  console.log(update);
}
```




在**任何节点**中，我们可以通过访问 `config` 和 `store` 作为节点参数来访问 `memoryStore` 和 `user_id`。下面是我们如何在节点中使用语义搜索来查找相关内存的示例：

```typescript
import { MessagesZodMeta, Runtime } from "@langchain/langgraph";
import { BaseMessage } from "@langchain/core/messages";
import { registry } from "@langchain/langgraph/zod";
import * as z from "zod";

const MessagesZodState = z.object({
  messages: z
    .array(z.custom<BaseMessage>())
    .register(registry, MessagesZodMeta),
});

const updateMemory = async (
  state: z.infer<typeof MessagesZodState>,
  runtime: Runtime<{ user_id: string }>,
) => {
  // 从 config 中获取 user id
  const userId = runtime.context?.user_id;
  if (!userId) throw new Error("User ID is required");

  // 命名空间化内存
  const namespace = [userId, "memories"];

  // ... 分析对话并创建新内存

  // 创建一个新的内存 ID
  const memoryId = uuidv4();

  // 我们创建一个新内存
  await runtime.store?.put(namespace, memoryId, { memory });
};
```


如上所示，我们也可以在任何节点中访问 store 并使用 `store.search` 方法来获取内存。请记住，内存以可转换为字典的对象列表形式返回。



```typescript
memories[memories.length - 1];
// {
```

## Checkpointer 库 (Checkpointer libraries)

在底层，检查点功能由遵循 [`BaseCheckpointSaver`](https://reference.langchain.com/javascript/classes/_langchain_langgraph-checkpoint.BaseCheckpointSaver.html) 接口的 checkpointer 对象驱动。LangGraph 提供了几种 checkpointer 实现，它们都通过可独立安装的库实现：



* `@langchain/langgraph-checkpoint`: Checkpointer Saver（[BaseCheckpointSaver](https://reference.langchain.com/javascript/classes/_langchain_langgraph-checkpoint.BaseCheckpointSaver.html)）和序列化/反序列化接口（[SerializerProtocol](https://reference.langchain.com/javascript/interfaces/_langchain_langgraph-checkpoint.SerializerProtocol.html)）的基础接口。包含用于实验的内存检查点实现（[MemorySaver](https://reference.langchain.com/javascript/classes/_langchain_langgraph-checkpoint.MemorySaver.html)）。LangGraph 默认包含 `@langchain/langgraph-checkpoint`。
* `@langchain/langgraph-checkpoint-sqlite`: 使用 SQLite 数据库（[SqliteSaver](https://reference.langchain.com/javascript/classes/_langchain_langgraph-checkpoint-sqlite.SqliteSaver.html)）的 LangGraph Checkpointer 实现。非常适合实验和本地工作流程。需要单独安装。
* `@langchain/langgraph-checkpoint-postgres`: 使用 Postgres 数据库（[PostgresSaver](https://reference.langchain.com/javascript/classes/_langchain_langgraph-checkpoint-postgres.index.PostgresSaver.html)）的高级 Checkpointer，用于 LangSmith。非常适合在生产环境中使用。需要单独安装。


### Checkpointer 接口 (Checkpointer interface)



每个 Checkpointer 都遵循 [`BaseCheckpointSaver`](https://reference.langchain.com/javascript/classes/_langchain_langgraph-checkpoint.BaseCheckpointSaver.html) 接口，并实现以下方法：

* `.put` - 使用其配置和元数据存储检查点。
* `.putWrites` - 存储与检查点关联的中间写入（即 [待处理写入](#pending-writes)）。
* `.getTuple` - 使用给定配置（`thread_id` 和 `checkpoint_id`）获取检查点元组。这用于在 `graph.getState()` 中填充 `StateSnapshot`。
* `.list` - 列出与给定配置和过滤条件匹配的检查点。这用于在 `graph.getStateHistory()` 中填充状态历史。


### 序列化器 (Serializer)

Checkpointer 在保存图状态时，需要序列化状态中的通道值。这是使用序列化器对象完成的。



`@langchain/langgraph-checkpoint` 定义了实现序列化器的协议，并提供了一个默认实现，可以处理各种类型，包括 LangChain 和 LangGraph 的原始类型、datetime、枚举等。


## 能力 (Capabilities)

### 人机协作 (Human-in-the-loop)

首先，Checkpointer 促进了 [人机协作工作流](/oss/javascript/langgraph/interrupts)，因为它允许人类检查、中断和批准图步骤。这些工作流需要 Checkpointer，因为人类必须能够在任何时间点查看图的状态，并且图必须能够在人类更新状态后恢复执行。有关示例，请参阅 [操作指南](/oss/javascript/langgraph/interrupts)。

### 内存 (Memory)

其次，Checkpointer 允许在交互之间保留“[内存](/oss/javascript/concepts/memory)”。在重复的人机交互（如对话）场景中，任何后续消息都可以发送到该线程，该线程将保留其对先前交互的记忆。有关如何使用 Checkpointer 添加和管理会话内存的信息，请参阅 [添加内存](/oss/javascript/langgraph/add-memory)。

### 时间旅行 (Time Travel)

第三，Checkpointer 允许进行“[时间旅行](/oss/javascript/langgraph/use-time-travel)”，使用户能够重放先前的图执行，以查看和/或调试特定的图步骤。此外，Checkpointer 使得可以从任意检查点分支图状态，以探索替代的执行路径。

### 容错 (Fault-tolerance)

最后，检查点还提供了容错和错误恢复功能：如果在给定超步中一个或多个节点失败，您可以从上一个成功的步骤重新启动图。此外，当图节点在给定超步中途执行失败时，LangGraph 会存储来自该超步中其他成功完成的节点的待处理检查点写入，这样当我们从该超步恢复图执行时，就不会重新运行成功的节点。

#### 待处理写入 (Pending writes)

此外，当图节点在给定超步中途执行失败时，LangGraph 会存储来自该超步中其他成功完成的节点的待处理检查点写入，这样当我们从该超步恢复图执行时，就不会重新运行成功的节点。
