我们非常欢迎代码贡献！无论您是修复错误（bug）、添加新功能，还是提高性能，您的贡献都将为成千上万的开发者带来更好的开发体验。

## 入门指南

<Note>
    在提交大型**新功能或重构**之前，请先在 [论坛](https://forum.langchain.com/) 中讨论您的想法。这可以确保与项目目标保持一致，并避免重复劳动。

    这不适用于错误修复或小型改进，这些可以直接通过 Pull Request (PR) 贡献。请参阅下面的快速入门指南。
</Note>

### 快速修复：提交 Bug 修复

对于简单的错误修复，您可以立即开始：

<Steps>
    <Step title="复现问题">
        创建一个最小化的测试用例来展示该错误。维护者和其他贡献者应该能够在无需额外设置或修改的情况下运行此测试并观察到失败。
    </Step>

    <Step title="Fork 仓库">

        将 [LangChain](https://github.com/langchain-ai/langchainjs) 或 [LangGraph](https://github.com/langchain-ai/langgraphjs) 仓库 Fork 到您的个人 GitHub 账户

    </Step>

    <Step title="克隆并设置环境">

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # 例如，对于 LangChain:
        git clone https://github.com/parrot123/langchainjs.git

        # 对于 LangGraph:
        git clone https://github.com/parrot123/langgraphjs.git
        ```

        ```bash
        # 在您的仓库内部，安装依赖
        pnpm install
        # 创建所有包的构建以解析工作区依赖项
        pnpm build
        ```

    </Step>

    <Step title="创建分支">
        为您的修复创建一个新分支。这有助于保持您的更改井井有条，并使后续提交 PR 更加容易。

        ```bash
        git checkout -b your-username/short-bugfix-name
        ```
    </Step>

    <Step title="编写失败的测试">
        添加 [单元测试](#test-writing-guidelines)，这些测试在没有修复的情况下应该会失败。这使我们能够验证错误是否已解决，并防止未来出现回归问题。
    </Step>

    <Step title="进行更改">
        在修复错误时，请遵循我们的 [代码质量标准](#code-quality-standards)。进行**解决问题所需的最小更改**。
    </Step>

    <Step title="运行构建">
        运行构建命令以确保包仍能正确构建
        ```bash
        pnpm build
        # 或构建特定的工作区包
        pnpm --filter @langchain/core build
        ```
    </Step>


    <Step title="验证修复">
        确保测试通过并且没有引入回归。在提交 PR 之前，请确保所有本地测试均已通过。


        ```bash
        pnpm lint
        pnpm test

        # 对于涉及集成的错误修复，也请运行：
        pnpm test:int

        # 或从仓库根目录运行特定工作区包的测试
        cd libs/langchain-core
        pnpm test
        pnpm lint

        # 或从仓库根目录运行特定包的测试
        pnpm --filter @langchain/core test
        pnpm --filter @langchain/core lint
        ```

    </Step>

    <Step title="完善文档">
        如果行为有所更改，请更新 docstrings（文档字符串）；对于复杂的逻辑，请添加注释。
    </Step>

    <Step title="提交 Pull Request">
        遵循提供的 PR 模板。如果适用，请使用 [关闭关键字](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword) (例如 `Fixes #ISSUE_NUMBER`) 来引用您正在修复的问题，以便在合并 PR 时自动关闭该问题。
    </Step>
</Steps>

### 全面开发环境设置

对于持续开发或大型贡献：

1. 请查阅我们的 [贡献指南](#contribution-guidelines)，了解关于功能、错误修复和集成的具体要求。
2. 按照下面的 [环境设置指南](#development-environment) 完成环境搭建。
3. 理解 [仓库结构](#repository-structure) 和包的组织方式。
4. 了解我们的 [开发工作流程](#development-workflow)，包括测试和代码规范检查。

## 贡献指南

在开始为 LangChain 贡献代码之前，请花点时间思考一下您做出贡献的原因。如果您的唯一目标只是为简历添加“首次贡献”记录（或者您只是想快速获得一些成就），那么您可能更适合参加训练营或在线教程。

为开源项目做贡献需要时间和精力，但它也可以帮助您成为更好的开发者并学习新技能。然而，重要的是要了解，这可能比遵循培训课程更困难、更慢。话虽如此，如果您愿意花时间把事情做好，为开源做贡献是值得的。

### 向后兼容性

<Warning>
    除关键安全修复外，不允许对公共 API 进行破坏性更改。

    有关主要版本发布的详细信息，请参阅我们的 [版本控制策略](/oss/javascript/versioning)。
</Warning>

通过以下方式保持兼容性：

<AccordionGroup>
    <Accordion title="稳定接口">
        **必须保持**:
        - 函数签名和参数名称
        - 类接口和方法名称
        - 返回值结构和类型
        - 公共 API 的导入路径
    </Accordion>

    <Accordion title="安全更改">
        **可接受的修改**:

        - 添加新的可选参数/类型参数

        - 向类中添加新方法
        - 在不改变行为的情况下提高性能
        - 添加新的模块或函数
    </Accordion>

    <Accordion title="在进行更改之前">
        - **这会破坏现有的用户代码吗？**
        - 检查您的目标是否是公开的

        - 测试中是否存在现有的使用模式？
    </Accordion>
</AccordionGroup>

### 新功能

我们力求为新功能设定较高的标准。通常情况下，我们不会接受来自外部贡献者的新核心抽象，除非已经有一个问题证明了对此的迫切需求。这同样适用于基础设施和依赖项的更改。

一般来说，功能贡献的要求包括：

<Steps>
    <Step title="设计讨论">
        开一个 Issue 来说明：

        - 您正在解决的问题
        - 提议的 API 设计
        - 预期的使用模式
    </Step>

    <Step title="实现">
        - 遵循现有的代码模式
        - 包含全面的测试和文档
        - 考虑安全影响
    </Step>

    <Step title="集成考量">
        - 此功能如何与现有功能交互？
        - 有没有性能影响？
        - 是否引入了新的依赖项？

        我们将会拒绝那些可能导致安全漏洞或报告的功能请求。
    </Step>
</Steps>

### 安全指南

<Warning>
    安全至关重要。切勿引入漏洞或不安全的模式。
</Warning>

安全检查清单：

<AccordionGroup>
    <Accordion title="输入验证">
        - 验证和清理所有用户输入
        - 在模板和查询中正确转义数据

        - 切勿使用 `eval()`，因为这可能导致任意代码执行漏洞

    </Accordion>

    <Accordion title="错误处理">
        - 使用特定的异常类型
        - 不要向错误消息中暴露敏感信息
        - 实现适当的资源清理
    </Accordion>

    <Accordion title="依赖项">
        - 避免添加硬性依赖项
        - 保持可选依赖项的最小化
        - 审查第三方包是否存在安全问题
    </Accordion>
</AccordionGroup>

## 开发工作流程

### 测试要求

<Info>
    目录路径相对于您正在处理的包而言是相对的。
</Info>

所有代码更改都必须包含全面的测试。

#### 单元测试


**位置**: `src/tests/FILENAME_BEING_TESTED.test.ts`


**要求**:
- 不允许进行网络调用
- 测试所有代码路径，包括边缘情况
- 对外部依赖使用模拟 (mocks)


```bash
# 运行整个测试套件
pnpm test

# 或运行特定的测试文件
pnpm test src/tests/FILENAME_BEING_TESTED.test.ts

# 或运行特定的测试函数
pnpm test -t "the test that should be run"
```


#### 集成测试


**位置**: `src/tests/FILENAME_BEING_TESTED.int.test.ts`


集成测试需要访问外部服务/提供者 API（这可能会产生费用），因此默认情况下不会运行它们。

并非所有代码更改都需要集成测试，但请记住，在审查过程中，我们会单独要求/运行集成测试。

**要求**:
- 测试与外部服务的真实集成
- 使用环境变量来存储 API 密钥
- 如果凭证不可用，优雅地跳过


```bash
pnpm test:int
```


### 代码质量标准

贡献的代码必须遵守以下质量要求：

<Tabs>
    <Tab title="类型提示 (Type hints)">

        **要求**: 为所有函数提供完整的类型定义

        ```typescript
        function processDocuments(
            docs: Document[],
            processor: DocumentProcessor,
            batchSize: number = 100
        ): ProcessingResult {
            // ...
        }
        ```

    </Tab>

    <Tab title="文档">

        **要求**: 所有导出函数和接口使用 [JSDocs](https://jsdoc.app/about-getting-started)

        ```typescript
        /**
         * Document processing instance.
         */
        interface FooDocumentProcessor {
            /**
             * Process documents in batches.
             *
             * @param docs - List of documents to process.
             * @returns Processing results with success/failure counts.
             */
            process(docs: Document[]): ProcessingResult;
        }

        /**
         * Process documents in batches.
         *
         * @param docs - List of documents to process.
         * @param processor - Document processing instance.
         * @param batchSize - Number of documents per batch.
         * @returns Processing results with success/failure counts.
         */
        export function processDocuments(
            docs: Document[],
            processor: DocumentProcessor,
            batchSize: number = 100
        ): ProcessingResult {
            // ...
        }
        ```


        - 为所有参数和返回值添加文档说明
        - 为复杂函数包含使用示例
        - 文档化抛出的异常
        - 重点关注“为什么”而不是“是什么”
    </Tab>

    <Tab title="代码风格">

        **自动化**: 格式化和代码检查：

        ```bash
        pnpm lint    # 检查风格和类型
        pnpm format  # 应用格式
        ```


        **标准**:
        - 使用描述性的变量名
        - 分解复杂的函数（目标是少于 20 行）
        - 遵循代码库中现有的模式
    </Tab>
</Tabs>

### 测试编写指南

为了编写有效的测试，需要遵循一些良好的实践：


- 将测试封装在描述被测试组件的 `describe` 块中
- 使用自然语言描述测试名称
- 确保断言详尽无遗
- 仅对合理大小的数据对象使用快照 (snapshots)


<Tabs>
    <Tab title="单元测试">

        ```typescript
        describe("DocumentProcessor", () => {
            it("Should handle empty document list", () => {
                const processor = new DocumentProcessor();
                const result = processor.process([]);

                expect(result.success).toBe(true);
                expect(result.processedCount).toBe(0);
                expect(result.errors).toHaveLength(0);
            });
        });
        ```

    </Tab>

    <Tab title="集成测试">

        ```typescript
        describe("ChatOpenAI", () => {
            it("Should test with real API", () => {
                const chat = new ChatOpenAI();
                const response = chat.invoke("Hello");
            });
        });
        ```

    </Tab>

    <Tab title="Mock 用法">

        ```typescript
        describe("APIService", () => {
            it("Should call with retry", () => {
                const mockClient = new MockClient();
                const service = new APIService(client: mockClient);
                const result = service.callWithRetry();
            });
        });
        ```

    </Tab>
</Tabs>
