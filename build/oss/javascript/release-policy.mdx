    <Tab title="LangChain">


    LangChain 生态系统由不同的组件包组成（例如：`@langchain/core`、`langchain`、`@langchain/community`、合作伙伴包等）。


    ## 发布节奏 (Release cadence)


    随着 LangChain 1.0 的发布，`langchain` 和 `@langchain/core` 的**次要版本 (minor)** 发布（例如，从 `1.0.x` 到 `1.1.0`）遵循语义化版本控制，并且可能会频繁发布。次要版本包含新功能和改进，但不包含破坏性更改 (breaking changes)。


    补丁版本发布的频率很高，可能每周发布数次，因为它们仅包含错误修复和微小改进。

    ## API 稳定性 (API stability)


    LLM 应用的开发是一个快速发展的领域，我们不断从用户和社区中学习。因此，我们期望 `langchain` 和 `@langchain/core` 中的 API 将持续演进，以便更好地满足用户的需求。


    随着 LangChain 1.0 采纳语义化版本控制：
    - 公共 API 的破坏性更改仅在**主要版本**发布时发生（例如，`2.0.0`）。
    - 次要版本递增（例如，`1.0.0` 到 `1.1.0`）会在不引入破坏性更改的情况下添加新功能。
    - 补丁版本递增（例如，`1.0.0` 到 `1.0.1`）包含错误修复和微小改进。

    我们通常会努力避免不必要的更改，并且会为被移除的功能提供弃用策略。

    ### 其他包的稳定性

    LangChain 生态系统中其他包的稳定性可能有所不同：

    - **LangChain 维护的合作伙伴包**（如 `langchain-openai` 和 `langchain-anthropic`）遵循语义化版本控制，并在 1.0 发布后预计保持稳定。其他合作伙伴包可能遵循不同的稳定性和版本控制策略，用户应参考这些包的文档以获取更多信息。


    - **`@langchain/community`** 是一个由社区维护的包，包含第三方集成。由于社区贡献和第三方依赖的性质，`@langchain/community` 不遵循与 `langchain` 和 `@langchain/core` 相同的严格语义化版本控制策略。有关更多详细信息，请参阅“长期支持 (Long-term support)”下的“特殊注意事项”部分。


    ## 弃用策略 (Deprecation policy)

    在提供更好的替代方案之前，我们通常会避免弃用功能。


    根据 LangChain 1.0 的语义化版本控制方法，被弃用的功能将在整个 1.x 发布系列中继续工作。破坏性更改（包括移除被弃用的功能）仅在**主要版本**发布时发生（例如 2.0）。

    当一个功能在 `langchain` 或 `@langchain/core` 中被弃用时，我们将：
    - 在代码和文档中明确标记其为已弃用
    - 提供迁移指南至推荐的替代方案
    - 在所有 1.x 次要版本中为被弃用的功能提供安全更新


    在某些情况下，如果被弃用的功能没有引起维护问题，我们可能会允许它们在代码库中保留更长时间，以进一步减轻用户的负担。

    ## 长期支持 (LTS)

    LangChain 遵循长期支持 (LTS) 策略，为生产应用提供稳定性：

    ### 发布状态定义

    软件包被标记为以下状态之一：
    - **ACTIVE (活动)**：当前正在积极开发中，包括错误修复、安全补丁和新功能。
    - **MAINTENANCE (维护)**：接收所有安全补丁和关键错误修复，但不接收新功能。

    ### 当前 LTS 版本

    **LangChain 1.0** 被指定为 LTS 版本：
    - **状态**：在 2.0 发布之前为 ACTIVE
    - **支持周期**：2.0 发布后，1.0 将进入 MAINTENANCE 模式，至少持续 1 年
    - **Semver 合规性**：用户可以在次要版本之间升级（例如，从 1.0 到 1.1），而不会遇到破坏性更改

    ### 旧版本支持 (Legacy version support)

    **LangChain 0.3**：
    - **状态**：MAINTENANCE 模式
    - **支持周期**：直到 2026 年 12 月
    - **支持内容**：安全补丁和关键错误修复

    ### 特殊注意事项


    **@langchain/community 1.0**：由于社区贡献和第三方集成的性质，`@langchain/community` 在次要版本中可能存在破坏性更改。

    <Tab title="LangGraph">
    LangGraph 遵循结构化的发布策略，以确保构建生产应用的用户的稳定性和可预测性。

    ## 发布节奏 (Release cadence)

    我们预计**主要版本 (major)** 的间隔至少为 6-12 个月，以为生产应用提供稳定性。

    **次要版本 (Minor)** 通常每 1-2 个月发布一次，包含新功能和改进。

    **补丁版本 (Patch)** 根据需要发布，通常每周一次，以解决错误和安全问题。

    ## API 稳定性 (API stability)

    ### 稳定 API (Stable APIs)

    所有没有特殊前缀的 API 均被视为稳定，可用于生产环境。我们在一个主要版本范围内维护稳定功能的向后兼容性。

    ### Beta 功能

    文档中标注为 `beta` 的功能具有以下特性：

    - 功能完备且经过测试
    - 可安全用于生产环境，但需理解其可能会有变动
    - 可能根据用户反馈进行小的 API 调整

    ### 实验性功能 (Experimental features)

    标记为 `experimental` 或 `alpha` 的功能：

    - 处于活动开发中
    - 可能会发生重大更改或被移除
    - 在生产环境中使用时应谨慎

    ### 内部 API (Internal APIs)

    以下划线 (`_`) 作为前缀或明确标记为内部的 API：

    - 不属于公共 API 的一部分
    - 可能会在没有通知的情况下更改
    - 不应被直接使用

    ## 弃用策略 (Deprecation policy)

    弃用功能时：

    1. **弃用通知**：功能将被标记为已弃用，并附带清晰的迁移指南
    2. **宽限期**：被弃用的功能至少保持可用一个次要版本
    3. **移除**：功能仅在**主要版本**发布中被移除
    4. **迁移支持**：我们提供迁移指南，并在可能的情况下提供自动化工具

    ## 平台兼容性 (Platform compatibility)



    ### JavaScript/TypeScript 支持

    - 我们支持 Node.js 的 LTS (长期支持) 版本
    - 所有公共 API 都提供 TypeScript 定义
    - 客户端组件的浏览器兼容性会进行文档说明


    ## 破坏性更改 (Breaking changes)

    破坏性更改仅在主要版本中引入，包括：
    - 移除被弃用的 API
    - 更改必需的参数
    - 影响现有应用程序的默认行为更改
    - 最低 Python/Node.js 版本更新

    ## 迁移支持 (Migration support)

    对于主要版本升级，我们提供：
    - 全面的迁移指南
    - 在可行的情况下提供自动化迁移脚本
    - 对前一个主要版本的扩展支持期
    - 所有破坏性更改的清晰文档记录

    ## 长期支持 (LTS)

    LangGraph 遵循长期支持 (LTS) 策略，为生产应用提供稳定性：

    ### 发布状态定义

    软件包被标记为以下状态之一：
    - **ACTIVE (活动)**：当前正在积极开发中，包括错误修复、安全补丁和新功能。
    - **MAINTENANCE (维护)**：接收所有安全补丁和关键错误修复，但不接收新功能。

    ### 当前 LTS 版本

    **LangGraph 1.0** 被指定为 LTS 版本：
    - **状态**：在 2.0 发布之前为 ACTIVE
    - **支持周期**：2.0 发布后，1.0 将进入 MAINTENANCE 模式，至少持续 1 年
    - **Semver 合规性**：用户可以在次要版本之间升级（例如，从 1.0 到 1.1），而不会遇到破坏性更改

    ### 旧版本支持 (Legacy version support)

    **LangGraph 0.4**：
    - **状态**：MAINTENANCE 模式
    - **支持周期**：直到 2026 年 12 月
    - **支持内容**：所有安全补丁和关键错误修复
